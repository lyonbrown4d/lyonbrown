Lyonbrown User and Developer Guide

Development and verification

The workspace uses Rust edition 2024. Cargo workspace declarations and Cargo.lock manage product dependencies. The root Cargo.toml records the minimum Rust version in rust-version. Engineering constraints live in the root AGENTS.md.

Async entry points prefer #[tokio::main]. Clap, Serde and fluxdi macros provide argument parsing, serialization and dependency injection. RunStatus and Tool use derives from fixed strum 0.28.0 for snake_case static-string conversion; error types reuse existing thiserror derives. CEF helper and Windows SCM dispatch run before runtime initialization. GPUI retains its main-thread event loop; explicitly owned or shared runtimes remain part of its composition.

Run locally during development

The repository’s .cargo/config.toml defines the dev alias. It uses Cargo directly, with no additional task runner to install. Run one command from the repository root to build the required binaries, start a development agentd and open the client:

cargo dev desktop
# Or open the terminal UI:
cargo dev tui

Run cargo dev tui in multiple terminals alongside Desktop. Clients using the same data directory, address and configuration share one development agentd. The command supplies the connection address and credentials automatically; no separate daemon startup is required.

Defaults are .local/dev/agentd for persistent development data and http://127.0.0.1:7547 for the endpoint. cargo clean preserves the data. These commands supervise foreground development processes without registering or replacing OS services. The terminal that first starts the daemon keeps its supervisor running after its client closes. Press Ctrl+C there to stop the development daemon. Later terminals reuse the daemon and can exit their clients without stopping it.

Startup checks are serialized for each data directory to prevent concurrent clients from creating multiple daemons. Reuse requires an authenticated handshake and matching node identity, protocol, build and configuration. An endpoint occupied by an unrelated process, invalid credentials or a different live build/configuration produces an error and leaves the existing process running. To use a new build or configuration, stop the development daemon in its original terminal and run the command again.

Relative paths resolve from the repository root and may contain spaces. Use matching options for all clients. Development requires a nonzero loopback port other than the product default 7447:

cargo dev desktop --dry-run
cargo dev tui --data-dir .local/dev/demo --listen 127.0.0.1:7548 --config /absolute/path/dev.toml
cargo dev desktop --data-dir .local/dev/demo --listen 127.0.0.1:7548 --config /absolute/path/dev.toml
cargo dev --help

The Cargo alias invokes apps/agent-dev with an argument array, without a platform shell or an extra task runner. The root README.md lists common commands; cargo --list also displays the dev alias.

cargo dev tui expands to cargo run --locked -p agent-dev -- tui. On first use, Cargo downloads and compiles Rust dependencies from Cargo.lock; no cargo install step is needed for the launcher, just or cargo-make. Platform build dependencies for GPUI and optional native SDKs still need to be available; see the local distribution guide.

Product and Gateway builds share typed Cargo message decoding from cargo_metadata 0.23.1. Only binary targets with the requested name supply executable paths; compiler diagnostics are forwarded, output is drained, and the process exit status is then checked. Build children use process-wrap Unix process groups or Windows JobObjects so cancellation cleans up the owned build tree. Interactive clients retain foreground terminal input.

Use cargo dev daemon when a separate foreground daemon is useful. Other development clients automatically connect to and reuse it.

The default configuration is config.toml inside the development data directory, with .env beside it. --config selects an existing TOML file. The commands do not create or overwrite configuration or dotenv files. Model, tool and log settings use the shared agent-config layering rules. agentd, TUI, Desktop and the development launcher all use shared agent-telemetry logging. Files default to the development data directory’s logs subdirectory, use separate process prefixes and follow the configured rotation and retention settings. The launcher forces the selected development address and data directory, reads that directory’s auth.token and ignores inherited connection credentials. Tokens pass only through the client child environment, never command arguments or launch output.

--dry-run displays the launch plan without creating directories, reading tokens or starting product processes; the outer Cargo command may compile agent-dev. Default Desktop/TUI builds enable neither native-cef nor native-computer; their browser execution and native computer hosting capabilities report unavailable. See the local distribution guide for the full CEF SDK, helper and application bundle layout.

Gateway full-stack development

The repository’s separate cargo gateway alias invokes the gateway-dev binary in apps/agent-dev. It starts neither agentd nor an OS service. Prepare existing TOML, administrator username/password and an independent API Key as described in AI Gateway, then run from the repository root:

cargo gateway --config /absolute/path/gateway.toml --data-dir /absolute/path/gateway-data
cargo gateway --help
cargo gateway --dry-run --config /absolute/path/gateway.toml
cargo gateway --build-only
cargo gateway --build-only --release

The launcher checks the current Rust toolchain’s wasm32-unknown-unknown target and prepares it through rustup if missing. It then checks cargo-leptos in the repository’s .local/tools/bin, installing it with cargo install --locked --root <repo>/.local/tools cargo-leptos --version 0.3.11 if absent. Existing tools must match the fixed version; no manual global installation is required. Rust, platform build tools and network access for downloads still need to be available.

Standard cargo-leptos leptos build --project gateway builds the application; --release selects release settings for both server and WASM. The launcher then runs an incremental Cargo build with matching settings and reads the executable path from the typed compiler-artifact messages described above, preserving Cargo target-directory and target configuration. The launcher reads workspace metadata through cargo_metadata::Metadata and validates Gateway project fields and site-directory scope. The workspace configuration selects .local/gateway-web/site as the default site root. Gateway receives absolute LYONBROWN_GATEWAY_WEB_ROOT and serves generated JavaScript and WASM under /ui/pkg/.

--build-only exits after building the server and assets, without starting Gateway. --dry-run prints the plan without running tools, reading credentials or creating runtime data; the outer Cargo command may still compile the launcher. Relative --config and --data-dir paths resolve from the repository root. Runtime data defaults to .local/gateway-web/data; --listen can select a nonzero loopback port. Ctrl+C in the launch terminal cleans up only the Gateway process owned by that launcher.

Gateway reads .env beside its runtime configuration, with process environment taking precedence. Keep runtime configuration and credentials in a separate directory: the launcher does not explicitly pass Gateway credentials to build commands, but official cargo-leptos itself reads workspace or parent-directory .env. This is not an absolute guarantee that build tools cannot access runtime credentials. Never put passwords or API Keys in source, build arguments or static assets.

Shared Rust Leptos components build with ssr for the server and hydrate for browser WASM. Signals manage policy drafts and submission feedback; official ServerAction / ActionForm handle forms, and tables use the public leptos-struct-table TableRow rendering interfaces for direct SSR output. Generated JavaScript boots WASM without a separate Node frontend stack. Authentication, CSRF, roles and policy-version checks remain server responsibilities.

Distribution includes both ai-gateway and site assets from the standard full-stack build. Absolute LYONBROWN_GATEWAY_WEB_ROOT selects a directory containing ui/pkg, defaulting to web beside the executable. Running only cargo run -p ai-gateway does not generate browser assets; missing or empty JS/WASM files fail startup explicitly. Build success does not establish browser hydration, form interaction or cross-platform runtime acceptance. See runtime evidence for its recorded scope.

Native computer client builds

CLI and Desktop disable native-computer by default. It explicitly forwards to agent-computer-runtime/native, which enables agent-computer/native. Default cargo dev desktop and cargo dev tui builds do not enable it automatically; native-cef does not enable computer hosting either. The development launcher supports explicit client feature selection:

cargo dev desktop --native-computer
cargo dev tui --native-computer
cargo dev desktop --native-computer --dry-run

The flag affects only the client build, without forwarding to agentd or changing computer_tools configuration. cargo dev daemon --native-computer is rejected. Clients can also be built and started separately:

cargo build -p agent-cli -p agent-desktop --features agent-cli/native-computer,agent-desktop/native-computer --locked
cargo run -p agent-cli --features native-computer -- computer targets
cargo run -p agent-desktop --features native-computer

Clients connect to or reuse the native daemon service through the shared launcher; the foreground development daemon is described above. The native feature does not change the daemon’s computer_tools = false default or replace OS permissions, interactive session checks or exact action approval. Neither default nor test dependencies implicitly enable native SDKs through Cargo feature unification. See terminal and desktop clients for selection, attachment and detachment.

Compilation establishes only that the code builds on the selected host. Native discovery, GUI selection, client-to-Harness attachment, observation and approved input require actual runtime acceptance. macOS follows the session identity and lock-field policy, returning SessionStateUnknown when state cannot be established. Read-only permission checks, rejection paths and synthetic-host regressions do not establish native-control acceptance. Real capture, approved input, locking and session switching still require runtime acceptance; actual Windows and Linux runtime acceptance also remains incomplete.

Verification commands

Run from the repository root:

cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build --workspace
mdbook build docs/zh
mdbook build docs/en

These commands check formatting, static issues, tests, compilation and documentation generation. They do not replace real-model requests, GUI startup, CEF operation, system permissions or cross-device acceptance. Report the command, environment, scenario and remaining coverage limits together.

Module changes

Clients own presentation and input. Models, tools, permissions and durable state remain in the daemon. Add shared fields to proto/agent/v1/agent.proto and update both consumers; do not put execution-library internals in protocol messages.

Assess responsibility-based decomposition when a handwritten source file reaches 300 lines. Integration tests belong in each crate’s tests/ directory. Avoid production panic, unwrap and uncontrolled unsafe. Necessary FFI stays at platform adapter boundaries with its safety conditions documented.

Maintain the books

mdbook serve docs/zh --open
mdbook serve docs/en --open

Both languages use matching chapter structures with separate prose. Describe source mechanisms, configuration and limits; distinguish source implementation, compilation, tests and runtime acceptance. Keep mdBook’s native theme. Shared diagram extensions are in docs/theme; browser dependency versions and licenses are recorded in docs/theme/VENDOR.md.

Use Mermaid code fences for new diagrams. The browser adapter provides rendering and image interaction without an additional documentation preprocessor. After changing shared diagram assets, build both books and check light/dark themes, zoom, pan, keyboard dismissal and SVG download.

Model protocol and decision regression

agent-test-support provides a shared local HTTP mock server. Integration tests in agent-runtime and agent-decision use the real protocol adapters for Responses, Chat Completions and Anthropic Messages without paid model calls. They cover structured output, authority restrictions, low confidence, conservative fallback, timeout and cancellation. Daemon tests also inspect actual tool behavior and durable events; mock output alone does not establish successful execution.

cargo test -p agent-runtime -p agent-decision -p agentd --locked
cargo test -p agent-mcp --features test-fixtures --locked

apps/agentd/tests/computer_tools.rs uses local model mocks, the real adapters for all three standard protocols, the Harness and an injectable synthetic attach_host. It checks observation, exact approval and denial, renewal through model and approval latency, configuration/host/input-permission restrictions, and durable Uncertain with no replay after lost or corrupted receipts and recovery. Assertions inspect input counts, approvals, execution receipts, events and Outbox. These tests perform no OS input and do not replace actual CLI/Desktop native attachment checks or establish desktop-control acceptance on three platforms.

cargo test -p agentd --test computer_tools --locked

Real local-model tests are explicitly ignored and require an existing chat GGUF file. Each command checks only the selected backend, model and current host:

LYONBROWN_TEST_GGUF=/absolute/path/model.gguf cargo test -p agent-inference --features llama --test native_models -- --ignored --nocapture
LYONBROWN_TEST_GGUF=/absolute/path/model.gguf cargo test -p agent-inference --features mistral --test native_models -- --ignored --nocapture

Isolated Computer target window

cargo run --locked -p agent-desktop --example desktop-computer-target

This example provides only a synthetic button and text field. It starts no daemon, model or ComputerRuntime and requests no screen-recording or Accessibility permissions. Startup prints a fresh .local/acceptance/computer-target-* directory; state.json retains click_count and text after exit. Each run creates a separate target for native-control acceptance. Interacting with this fixture does not establish Harness or approval-path acceptance.

Reusable decision and Gateway checks

cargo test --locked -p decision-core -p decision-model -p decision-semantic
cargo test --locked -p gateway-core -p gateway-storage -p ai-gateway
cargo test --locked -p gateway-web --no-default-features --features ssr
cargo test --locked -p agent-dev --test gateway_commands
cargo check --locked -p gateway-web --no-default-features --features hydrate --target wasm32-unknown-unknown
cargo gateway --build-only
cargo check --locked -p decision-core --no-default-features
cargo run --locked -p decision-core --no-default-features --example embedded
cargo check --locked -p decision-semantic --features semantic-local

The WASM check requires the current toolchain’s wasm32-unknown-unknown target; cargo gateway prepares it before building. SSR tests cover server pages, Server Functions and security boundaries. The hydrate check validates the browser build, without replacing real-browser acceptance of events, forms and asset loading.

Real embedding acceptance uses LYONBROWN_TEST_EMBEDDING_CONFIG to select an OfflineEmbeddingConfig JSON with absolute paths and SHA-256 values for each asset. Only the explicit test below loads those weights; default workspace tests neither download nor load models:

LYONBROWN_TEST_EMBEDDING_CONFIG=/absolute/path/offline-embedding.json cargo test --locked -p decision-semantic --features semantic-local --test offline caller_supplied_real_model_replays_bilingual_queries_with_measured_thresholds -- --ignored --exact --nocapture

The test uses disjoint calibration and replay fixtures to check real loading, dimensions, thresholds and Unknown behavior. Its small sample is not a production multilingual accuracy benchmark. See Reusable decision engine for APIs and AI Gateway for startup, keys and Swagger.

Native service acceptance

The following macOS test registers a real launchd service. Use a test account with no Lyonbrown service registration and an unused 127.0.0.1:7447. Build the product daemon, then provide its absolute path:

cargo build -p agentd --bin agentd --locked
LYONBROWN_SERVICE_AGENTD=/absolute/path/agentd cargo test -p agent-launch --test native_service --locked -- --ignored --nocapture --test-threads=1

The test checks that two clients reuse the same service, another data directory cannot replace it, and a native service restart preserves node identity and session records. On success it verifies registration ownership and idle state before removing its own service and data. On failure it preserves the data so a live daemon keeps its executable and store; inspect service.json and native service state before handling any remaining registration.

This path passed with the actual product binary on macOS 27.0.1, arm64, without model calls or Keychain authorization. It does not replace OS installation acceptance for the PKG or establish Windows SCM or Linux systemd runtime behavior.

Publish the documentation site

Documentation is built locally and published from a GitHub Pages branch. Run mdbook build docs/zh and mdbook build docs/en. Place docs/index.html at the publication root, put the two generated books under zh/ and en/, and add an empty .nojekyll file at the root. Cargo artifacts, local configuration and credentials are excluded.

Commit the static files to the separate gh-pages branch. Configure Pages with build type legacy, using / on that branch. Check both languages’ local resources and links before pushing, then inspect the Pages build and read back the public site. A successful branch push alone does not establish a successful deployment.

.github/workflows/pages.yml remains a manual publishing entry for environments with GitHub Actions enabled; switch the Pages source to GitHub Actions before using it. The manual branch deployment does not invoke that workflow.
