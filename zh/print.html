Lyonbrown 使用与开发文档

项目概览

Lyonbrown 将 Agent 执行放在常驻的 agentd 进程中。终端客户端和 GPUI 桌面通过认证协议访问会话、任务和事件。客户端只负责输入、呈现和连接状态；关闭窗口不构成取消任务的指令。

本文档面向本地使用者和开发者，与当前 Rust 工作区对应。首次运行参阅本地运行，理解执行和恢复机制参阅会话、任务与恢复。文档中的源码机制说明不代表真实模型、原生 SDK 或跨设备场景已经验收。

本地运行

先准备根 Cargo.toml 要求的 Rust 工具链。模型、原生图形和浏览器 SDK 的前置条件取决于启用的能力；缺少原生依赖时不能仅凭 crate 名称认定该能力可用。

启动开发环境

在仓库根目录直接使用 Cargo 选择客户端，无需安装额外任务工具：

cargo dev tui
# 或启动桌面客户端
cargo dev desktop

命令自动构建、启动或复用开发 agentd，并传入客户端连接配置。多个终端与 Desktop 可共用默认的 .local/dev/agentd 数据目录和 127.0.0.1:7547 地址。数据目录、配置与停止方式见开发与验证。

独立运行 daemon

在仓库根目录执行：

cargo run -p agentd -- --data-dir /path/to/lyonbrown-data

默认监听 127.0.0.1:7447，本地客户端入口只允许回环地址。daemon 在数据目录中保存节点身份、auth.token 和 agent.sqlite3，并独占该目录。另一个 daemon 使用相同目录时会失败，避免多个进程同时写入节点状态。

模型请求由 daemon 发出。启动前通过进程环境或配置文件旁的 .env 提供 OPENAI_API_KEY；选择 anthropic 时使用 ANTHROPIC_API_KEY。不要将真实凭证提交到仓库。未提供模型凭证时不能执行真实模型请求。

--data-dirLYONBROWN_DATA_DIR系统用户本地数据目录
--providerLYONBROWN_PROVIDERopenai；还支持 openai-responses、openai-completions、anthropic
--modelLYONBROWN_MODELgpt-4.1；模型是否可用取决于提供方与凭证

supports_images 默认 false，仅在提供方和所选模型均支持图片时显式开启 --supports-images 或 LYONBROWN_SUPPORTS_IMAGES=true。分类器、配置示例与协议对应关系见模型与执行决策。

所有产品进程通过共享 agent-telemetry，使用 tracing、tracing-subscriber 与 tracing-appender 写入 JSON 行日志，默认位于数据目录的 logs，按天轮转，每个进程前缀保留 14 个文件。LYONBROWN_LOG_DIRECTORY 和 LYONBROWN_LOG_RETENTION 可覆盖目录与保留数量；保留数量允许 1..=365。凭证不进入 UI 模型或配置调试输出。

直接运行客户端与原生服务

开发时使用 cargo dev tui 或 cargo dev desktop 自动启动并连接共享开发 daemon，参数见开发与验证。安装后的终端与 Desktop 在连接本机默认地址时，通过共享 launcher 检查并复用同一用户的原生服务，校验版本、协议和能力。macOS 使用 launchd，Linux 使用 systemd 用户服务；Windows 使用按当前用户 SID 区分的 SCM 服务。

服务注册锁和 service.json 固定保存在默认用户数据目录，不随客户端的 --data-dir 改变。已有服务使用其他数据目录时，launcher 会拒绝替换；修改客户端目录不能注册第二个同名服务。认证令牌仍保存在该 daemon 实际使用的数据目录中。

Windows 先安装 MSI，再从开始菜单运行 Set up Lyonbrown service。设置入口要求同一 Windows 账号完成 UAC 提权，并在原生凭据窗口输入服务登录密码；切换到另一个管理员账号会被拒绝。CLI 与 Desktop 共享 Program Files 中受保护的 daemon，密码不会进入命令行或配置文件。服务升级等待活动任务结束，并检查存储兼容范围与回滚条件。

直接使用 cargo run 连接本机默认地址时，客户端也会检查原生服务，因此要求能找到完整安装包中的 daemon，或同目录下已构建的 agentd。开发时优先使用上面的 cargo dev 命令；以下命令用于直接运行终端：

cargo run -p agent-cli -- --endpoint http://127.0.0.1:7447 --data-dir /path/to/lyonbrown-data

客户端通过 --token、LYONBROWN_TOKEN 或配置文件旁的 dotenv 接收 token。本机默认地址由共享 launcher 从所复用 daemon 的数据目录读取 auth.token；其他地址必须显式提供 token。令牌不应写入文档、Git 或聊天记录；通过环境变量或本地文件提供可避免将值写入命令历史。

选项环境变量默认值或行为
--endpointLYONBROWN_ENDPOINThttp://127.0.0.1:7447
--tokenLYONBROWN_TOKEN本机默认地址通过 launcher 读取 auth.token；其他地址须提供 token
--data-dirLYONBROWN_DATA_DIRProjectDirs::from("org", "Lyonbrown", "Lyonbrown") 的本地数据目录
--theme无auto；还可选 light、dark

--data-dir 应指向与 daemon 相同的数据目录，或通过环境变量提供相同 token。认证失败时先核对地址与令牌，不要反复提交 prompt。

连接成功后按 Ctrl+N 创建会话，输入消息并按 Enter。任务结果和审批来自 daemon。关闭客户端后可重新连接原会话查询结果。详细按键见终端与桌面客户端。

配置依据：apps/agentd/src/config.rs、crates/agent-config/src/load.rs、crates/agent-runtime/src/provider.rs 和 apps/agent-cli/src/config.rs。

模型与执行决策

每次运行先由 agent-decision 生成执行计划，再由 agent-runtime 打开 rpi-harness。分类器只返回建议，不执行工具，也不能授予权限。

执行计划如何生效

未配置 decision.model 时，daemon 使用显式工作区规则：通用模型、允许 read_file 和 write_file，并按配置及运行时能力提供 MCP、浏览器和受信任命令工具。配置且已配对的委派目标可启用分布式执行与 delegate_task。文件路径仍受工作区限制，变更操作仍须逐次审批。规则来自 daemon 配置，不从 prompt 中提取授权。

配置分类器后，daemon 将用户输入作为待分类数据发送。返回值必须是单个 JSON 对象，包含 task_kind、model_policy、allowed_tools、execution_mode、target_hint、risk_level 和 confidence。额外字段、无效枚举、错误类型或超出范围的置信度均被拒绝。

flowchart TB
    Input[已接受的用户请求] --> Select{配置了 decision.model?}
    Select -->|否| Rule[显式工作区规则]
    Select -->|是| Classify[无工具的分类请求]
    Classify --> Validate[JSON 与置信度校验]
    Validate -->|通过| Clamp[按 daemon 权限与能力限制建议]
    Validate -->|失败或超时| Fallback[本地通用模型 / 无工具]
    Rule --> Persist[保存 execution_plan 事件]
    Clamp --> Persist
    Fallback --> Persist
    Persist --> Filter[过滤 Harness 实际工具集合]
    Filter --> Run[rpi-harness 执行]
    Run --> Approval[有副作用的工具仍须人工审批]

工具集合取分类结果、已授权工具和可用能力的交集。模型策略、分布式执行和目标节点也分别受允许列表约束。委派目标必须同时出现在配置和有效配对记录中；本地执行计划不提供委派工具。分类器不能通过输出其他工具、策略或节点扩大权限。委派配置与审批范围见本地工具与浏览器操作。

有效计划先写入持久事件 execution_plan，其中包含工具、能力、执行模式、风险、置信度、来源及 trace_id，然后才打开 Harness。daemon 按该计划过滤实际工具集合，因此限制同时作用于模型可见工具和实际执行。审批按运行、工具、完整参数和有效期核对；分类器判断不能替代人工批准。

分类器不可用、超时、输出无效、置信度不足或缺少所需能力时，回退为本地通用模型、无工具、无目标节点。分类阶段取消会将运行保存为取消状态，不调用主模型。

本地推理边界

agent-inference 通过 llama-cpp-2 和 mistral.rs 提供本地推理适配。它们只生成模型输出；会话与 Agent Loop 仍由同一个 rpi-harness 管理。daemon 启动时加载配置的本地文件并注册模型，加载失败则不会就绪，也不会转用云端或自动下载模型。

provider = "local"
model = "local-main"

[[local_models]]
id = "local-main"
backend = "llama"
format = "gguf"
path = "/absolute/path/to/chat-model.gguf"
context_window = 4096
max_output_tokens = 512
parallel_requests = 1
max_model_bytes = 8589934592

路径和模型文件为示例，必须换成本机文件；Windows 应使用本机绝对路径。llama 需要构建 agentd 时启用 local-llama，mistral 需要 local-mistral。llama 读取 GGUF；Mistral 可选择 gguf 或 directory。文件、模型架构与量化格式仍须被所选推理库支持，扩展名相同不代表兼容。

本地配置使用 CPU，不隐式分配 GPU。max_model_bytes 限制输入文件大小，不表示运行时内存上限；上下文、输出 token 与并发量分别受配置约束。运行开始时，实际模型元数据写入 model_selected 事件。文本模型不声明图片或工具能力，daemon 会在保存执行计划和创建 Harness 前移除不受支持的工具。

分类器也可设置 decision.provider = "local"，并将 decision.model 指向已配置的本地模型 ID，与主模型独立选择。LocalClassifier 只接受无工具的结构化输出，仍受同一 JSON、置信度、超时和取消规则约束；格式不合格时保守回退。本地主模型不需要云端凭证。

运行方法与验收边界见开发与验证，MCP 配置见连接 MCP 工具。

连接 MCP 工具

agentd 使用 rmcp 连接配置中列出的 MCP 服务，支持 stdio 和 Streamable HTTP。连接与工具目录属于 daemon；客户端负责展示审批和结果，模型不能新增服务或修改连接参数。

配置服务与凭证

在共享数据目录的 config.toml 中列出服务，并明确允许调用的工具：

[[mcp]]
id = "reference"
allowed_tools = ["lookup"]

[mcp.transport]
type = "streamable_http"
url = "https://mcp.example.com/rpc"
headers = { Authorization = "MCP_AUTHORIZATION" }

这里的服务地址和工具名为示例，须与实际服务相符。headers 的值是环境变量名。在相邻 .env 或进程环境中设置对应变量，内容为服务要求的完整请求头值，例如 Bearer ...。进程环境覆盖 .env；缺少引用的变量时，daemon 启动失败。凭证不进入模型工具 Schema 或审批参数。

远程 HTTP 服务必须使用 HTTPS。HTTP 仅允许回环地址；URL 不得含用户名、密码、查询串或片段。客户端不跟随重定向，也不继承代理环境变量。

本地进程使用绝对可执行路径：

[[mcp]]
id = "local-reference"
allowed_tools = ["lookup"]

[mcp.transport]
type = "stdio"
executable = "/absolute/path/to/mcp-server"
arguments = ["--stdio"]
environment = { SERVER_TOKEN = "LOCAL_MCP_TOKEN" }

路径示例适用于 macOS/Linux；Windows 应填写本机绝对路径，可用 TOML 单引号字符串保留反斜杠。environment 将子进程变量名映射到 .env 或进程环境中的变量名。daemon 只传递明确引用的变量和少量系统运行变量，不把模型提供方密钥或整个父进程环境传给 MCP 子进程。stderr 写入私有日志目录，按服务保留有大小限制的诊断文件。

最多配置 64 个服务，所有服务合计最多允许 64 个工具。工具必须存在于服务返回的目录中，且输入必须是受支持的、有大小限制的对象 Schema。外部 Schema 引用被拒绝。

从模型调用到实际执行

模型通过 mcp_call 调用已选工具。call 对象内的服务、工具和参数必须匹配目录中的同一个分支：

{
  "call": {
    "server": "reference",
    "tool": "lookup",
    "arguments": { "query": "example" }
  }
}

参数同样是示例；实际字段由该服务的工具 Schema 决定。完整分支放在根级 call 属性内，使三个模型协议都能保留服务、工具与参数的对应关系。服务描述和结果均作为不可信数据处理。

daemon 先校验工具白名单和参数，再保存审批。审批绑定 Run、服务、工具、调用 ID、完整参数和有效期；批准后只消费一次，随后才派发请求。服务标注「只读」或模型给出高置信度，均不能跳过审批。未配置 MCP 时，执行计划和模型可见工具中不包含 mcp_call；决策分类器只能进一步收缩权限。

派发前取消不会发送工具调用。派发后取消、超时或连接丢失可能留下未知副作用，运行进入 Uncertain，不会自动重放。待处理审批随运行结束关闭；已经消费的审批保留原记录。恢复与核对规则见会话、任务与恢复。

MCP 返回的资源链接不自动读取；sampling 和 elicitation 不能借客户端扩大权限。输入消息、文本和图片输出均有大小限制。daemon 关闭时取消共享连接，已有 Run 的工具引用也不能再次调用。

源码：crates/agent-mcp、crates/agent-config/src/mcp.rs、apps/agentd/src/mcp.rs 与 apps/agentd/src/authorization.rs。

本地工具与浏览器操作

模型工具由 agentd 装配，客户端只显示调用、审批和结果。工具结果、网页内容及进程输出均不能授予额外权限。远程会话中的本地命令在 daemon 所在主机执行。

启用受信任命令

execute_command 默认关闭。管理员在 daemon 的 config.toml 中显式列出可执行文件的绝对路径，重启后才向模型提供此工具。例如以下 macOS 配置允许 /usr/bin/printf，并只向子进程传入指定的环境引用：

[commands]
executables = ["/usr/bin/printf"]

[commands.environment]
CHILD_KEY = "LYONBROWN_CHILD_VALUE"

LYONBROWN_CHILD_VALUE 必须存在于分层配置读取的 dotenv 或进程环境中。右侧是变量名，不能填写真实凭证。未解析的引用使配置加载失败。子进程不继承完整环境，参数直接传递给程序，不经过 shell；可执行文件和环境映射分别最多 64 项。

工作目录必须位于会话工作区内，默认为 .。这项约束不隔离程序的文件和网络访问：受信任程序仍拥有运行 agentd 的操作系统用户权限。允许解释器或 shell 会允许其参数表达更广泛的操作，应由管理员评估允许的程序及每次准确参数。

模型参数默认值与限制
executable必填，必须匹配绝对路径允许列表
arguments空数组，最多 256 个字符串
cwd.，相对会话工作区
timeout_ms30000，允许 1..=120000 毫秒
output_limit_bytes65536，允许 1..=1048576 字节

每次执行都要求人工批准准确动作，审批绑定会话、owner_epoch、运行、调用、动作标识、解析后的程序路径、参数、目录、超时和输出上限。daemon 再次核对会话所有权和运行状态，先保存执行意图再启动程序，随后保存结果回执。取消、执行结果或回执持久化无法确认时进入 Uncertain；不能因断线或相同调用再次出现而自动重放。核对持久回执与实际副作用后再决定下一步。

依据：crates/agent-config/src/commands.rs、crates/agent-workspace/src/process/、apps/agentd/src/commands/。回归入口为 apps/agentd/tests/command_tools.rs。

close_space当前会话的 space_id

navigatetab_id、当前 snapshot_id、revision，以及 text 中的目标 URL

变更操作要求准确动作人工审批。daemon 检查会话、所有者代次、runtime host 绑定、取消状态和人工接管状态。人工接管期间暂停模型变更；模型工具不开放原始输入和接管能力。快照过期后重新观察，未知结果先核对记录，禁止自动重放。Profile 保存不代表活页面恢复。

模型侧变更在同一本地事务中消费准确审批、保存浏览器执行意图，并写入事件和 Outbox；事务再次检查运行仍在执行、会话及所有者代次一致。事务失败时审批和意图一同回滚。提交后才向获批的 runtime host 发送操作；等待回执时取消或断线会保留 Uncertain，不重放动作。客户端的人工浏览器操作使用独立的认证入口，并保存相同类型的执行意图和结果回执。

原生 CEF 语义动作在滚动、聚焦、按键或导航之前撤销旧快照。进入这些步骤后，动作或后续观察失败会进入 Uncertain，停止本次模型运行，并保留持久回执供人工核对。输入、所有权和快照检查在动作之前完成。

人工接管的原始输入在聚焦或派发前撤销旧语义快照；进入这些步骤后的错误保存为 Uncertain，恢复不自动重放。成功输入本身不递增帧版本，允许同一帧的按下与松开配对；页面变化仍可使帧失效。

apps/agentd/tests/browser_tools.rs 通过本地 HTTP 模型 mock 和真实协议适配器覆盖 Responses、Chat Completions、Anthropic Messages，以及批准、拒绝、所有权/会话边界、取消和截图 artifact。其 runtime host 是合成实现，验证的是 Harness 到 daemon 的工具契约与持久状态，不能替代原生 CEF 自主浏览器操作验收。

原生链路使用 apps/agentd/tests/native_browser_tools.rs 单独验收。在 macOS 27.0.1 arm64 的调试 CEF 环境中，三个协议分别完成真实 AX 观察、准确审批后的填入与点击，并通过本地 HTTP 页面副作用和持久回执核对结果；另三种场景在点击成功后丢弃回执，确认取消与恢复不重放，运行保持 Uncertain。测试只操作合成页面和独立 Profile，使用调试测试钥匙串，不证明生产钥匙串或其他平台已验收。

模型计算机工具

computer_observe 与 computer_act 默认关闭。受信任的 daemon 配置使用顶层 computer_tools = true 启用，环境变量为 LYONBROWN_COMPUTER_TOOLS。computer_lease_secs 默认为 300 秒，允许 10..=300 秒，环境变量为 LYONBROWN_COMPUTER_LEASE_SECS；配置沿用共享分层规则。这些开关不建立原生连接。CLI/TUI 和 Desktop 必须另行显式选择目标并挂接到会话，操作见终端与桌面客户端。

向决策模型声明计算机能力前，daemon 必须找到同一自有 Session 和 owner_epoch 下、桌面范围已经固定的认证宿主，并确认能力响应的 can_control() 为真。仅连接成功、模型选择计算机能力或配置启用，都不能绕过屏幕与输入权限检查。工具由唯一的 Harness 执行，不创建另一套 Agent Loop。

computer_observe 接收可选的 screenshot（默认 false），返回 snapshot_id、revision、范围、窗口和有界 AX 语义，并标记 untrusted_desktop_content。语义输出限制为 1 MiB；截图按需编码为 PNG，返回 artifact 摘要，不把 RGBA 像素直接放入模型文本。桌面内容不能授予权限。

computer_act 要求上次观察的 snapshot_id、revision 和一个 action，支持 move、click、scroll、key、text。timeout_ms 默认 5000，范围为 1..=30000 毫秒。每次调用先消耗观察引用，重新捕获并比较原内容摘要；模型等待期间内容变化时，必须重新观察，不能静默采用新画面。内容一致后，Runtime 保留不可变的准备记录。

人工审批绑定动作、宿主、Session、owner_epoch、Run、模型调用、原观察引用、完整准备记录及超时。daemon 在同一本地事务中消费准确审批、保存执行意图、事件和 Outbox，提交后才发送 Execute。Runtime 按原租约和观察限制在输入前再次捕获；内容变化、租约失效或取消都会阻止输入，准备记录失败后也不能重放。已提交动作的实际响应保存为持久回执；取消、断线、无效回执或无法确认的结果进入 Uncertain，停止继续运行并要求核对，不自动重放。

Run 持有的续租任务在模型生成和人工审批等待期间维持当前有效令牌，每隔租期的三分之一尝试续租。它不能恢复已过期或撤销的控制权；Run 关闭时停止续租并撤销准确令牌，撤销失败则断开原连接。认证、传输限额与平台限制见协议与平台能力。

依据：apps/agentd/src/computer/tools/、apps/agentd/src/computer/mutation.rs、apps/agentd/src/execution.rs 与 crates/agent-computer-runtime/src/。合成宿主回归的覆盖范围见开发与验证，不能替代原生桌面运行验收。

委派给配对节点

delegate_task 默认关闭。先通过 daemon 的 peer-pair 操作核对完整 TLS 与 Noise 配对指纹，再在 config.toml 中列出允许的节点、HTTPS 地址与能力。发现结果和模型输出都不能添加配对或修改目标地址。

[[delegation_targets]]
node_id = "worker-example"
endpoint = "https://worker.example:7448"
capabilities = ["workspace.read"]

这段配置只声明允许的路由，不创建配对，也不授予 Worker 超出配对记录的能力。可用能力限于 workspace.read 与 workspace.write.approval；实际范围还受本次执行计划约束。只有允许分布式执行的计划才向 Harness 提供此工具，Worker 的子运行不继续委派。

模型通过 call 选择 dispatch、get、reconcile、cancel 或 accept。任务只能属于本次父 Run、会话、所有者与 owner_epoch。dispatch 要求目标、指令、能力和超时，daemon 为当前模型调用生成稳定的任务与尝试标识，避免重复调用产生第二次执行。

派发、取消和结果验收分别要求准确动作审批。派发审批绑定目标地址、完整配对指纹和任务范围；验收审批还绑定已核对结果的 SHA-256 摘要与原文。配对身份、会话所有权或结果变化后，旧审批失效。Worker 返回内容始终标为不可信，不能代替授权。

执行意图持久化后发生断线、取消或回执丢失，任务进入 Uncertain，本次运行停止并要求核对原任务。reconcile 查询同一任务身份，不重新派发。人工管理命令见客户端。

apps/agentd/tests/delegation.rs 通过三个模型协议的真实适配器、本地模型 mock、Master 与配对 mTLS Worker 的 Harness 验证派发、审批和结果验收，并覆盖拒绝、撤销配对、身份变化、跨父运行访问、范围扩大及未知结果禁止重放。

组件与调用关系

agentd 持有会话、任务、模型、工具和权限。agent-client 将 bearer token 放入 gRPC 请求元数据；终端与桌面通过同一套 ClientService 消息访问 daemon。rpi-harness 的具体类型保留在 runtime 适配层，不进入公共协议或 UI 模型。

模型与分布式任务

远程模型协议、本地推理引擎和决策分类器共用领域边界。模型元数据决定是否支持工具、图片和上下文规模；决策结果还要经过主机策略、实际可用能力和 Worker 授权范围限制。本地模型通过显式配置的路径加载，不自动下载或回退到云端。

会话、任务与恢复

Runtime 将工具交给主机适配器执行，主机负责授权、工作区约束和取消。Harness 自身的 provider 自动重试被禁用；重试策略属于持久任务编排。先保存执行意图，再产生副作用，是恢复时区分「未执行」与「结果未知」的依据。

快照与事件中的图像

Harness 快照保留原始消息内容。entry_appended 和 record_appended 则使用独立投影：图像块只保留 type、mimeType、dataRedacted 和 encodedBytes，不携带 Base64 内容。encodedBytes 表示原 Base64 字符串的字节数。该规则也适用于工具结果、压缩保留的消息、执行意图、排队消息和流式起始消息；Store、Outbox 与 WatchRun 使用同一投影载荷。投影发生在 Runtime 提交新事件时，读取既有事件不会重新计算载荷。

投影按已知消息类型处理图像，不递归删除任意 JSON 中的 data 字段。工具参数和自定义业务数据仍由对应适配器约束；无法识别的排队载荷或消息帧只返回 projectionOmitted 标记。输入图像的调试输出只含 MIME 和长度。

含图像会话的恢复暂不开放。恢复入口保留原快照并明确返回不可用，不调用模型或重放请求。原因是 rpi-ai 0.5.0 的原始 JSON 序列化会产生重复的 type 字段，见上游问题 #59。代码没有加入快照规范化适配。daemon 的 StartRun 接口仍只接收文本；Runtime 内部的图像输入不代表客户端支持图像会话。

断线与重启

客户端断线后，使用原会话重新查询运行状态。事件按运行 ID 和 cursor 排序，WatchRun 的 after_cursor 用于请求后续事件。事件流断开不能证明任务失败，也不能触发 prompt 重放。

存储层的 recover_interrupted 将执行中而没有持久终态的记录标记为 uncertain。尚未开始的 accepted 记录与已经进入执行的记录分开处理。Runtime 恢复 Harness 会话时检查未完成的工具记录：工具结果未提交时返回 Uncertain，不会猜测副作用是否发生。

恢复事务同时将对应运行的 pending 审批改为 cancelled，并写入 approval_closed、run_uncertain 事件及 Outbox。任一写入失败时，这些状态和事件一并回滚；重复恢复不再次生成记录。关闭旧审批不会解决运行的未知结果，也不会授权重放工具。

uncertain 仍属于未解决的运行，不能通过创建同会话的新运行绕过。应保留数据库、事件和对应外部操作证据，核对实际结果后再决定后续操作。当前协议没有通用的人工修改终态接口。

审批

审批保存工具名、参数、所属运行和过期时间。decide_approval 只接受尚未过期且仍处于等待审批的请求。消费审批时再次核对运行、工具和参数，并将审批状态改为 consumed，防止同一授权被重复使用。

Master 与 Worker

TaskStore 在更新 Worker Attempt 或采纳结果时校验 attempt_id 与 owner_epoch。成功的 Attempt 先进入 awaiting_acceptance；只有显式接受结果后 Task 才进入 completed。

Worker 启动恢复只处理持久分发目标为本机、Attempt 状态为 accepted 或 running 的记录，将其标记为 uncertain，同时保留所有权校验。发往其他节点的 Master 记录和未记录目标的通用 Task 保持原样；它们不会因 Worker 恢复而被改写。该操作不迁移 Master 所有权，也不重放 Attempt。

原生计算机连接

CLI/TUI 与 Desktop 在自身进程内嵌入 ComputerRuntime。默认构建不启用原生 SDK；需要显式构建客户端的 native-computer feature，见开发与验证。这不启用 daemon 的模型工具，也不请求操作系统权限。目标发现只列出已有权限下的窗口或显示器元数据，不截图、不发送输入；会话锁定、状态未知或缺少屏幕权限时会拒绝发现。

CLI 先列出目标，再用 daemon 中已有的非零 Session UUID 和一个目标 ID 显式挂接：

cargo run -p agent-cli --features native-computer -- computer targets
cargo run -p agent-cli --features native-computer -- computer attach --session SESSION_UUID --window WINDOW_ID --process-id PID
# 显示器范围使用 --display DISPLAY_ID，不传 --window 或 --process-id

computer targets 不连接 daemon。选择窗口时，需要同时复制目录中的窗口 ID 和 process_id。computer attach 重新发现目标，先核对 PID 完全一致，再保留描述符、建立认证连接并检查会话归属；窗口 ID 被其他进程复用时不会静默采用新目标。命令保持前台运行，按 Ctrl+C 断开；进程退出也撤销宿主连接。挂接失败会显示不可用原因，不自动选择其他目标。

TUI 在已连接并选定会话后，通过输入区执行本地命令：

/computer targets
/computer attach window WINDOW_ID
/computer attach display DISPLAY_ID
/computer status
/computer detach

两个 attach 示例择一使用。必须先运行 /computer targets，再从当前目录选择；挂接使用缓存中的准确目标描述符，不按 ID 临时替换目标。Computer 区显示原绑定会话、范围和连接状态，Alt+PageUp / Alt+PageDown 滚动详情。切换会话不转移已有连接；换目标或会话前先 detach。/computer 前缀即使语法错误也不会提交给模型。重连或断线会撤销宿主并清空目标目录，重新挂接前必须再次发现；动作不会自动重放。

Desktop 的操作与绑定状态见下方「Computer 面板」。目标目录与权限、固定窗口身份的限制见原生桌面执行边界。入口接线不等于原生控制验收；macOS 按会话身份与锁字段策略检查，状态未知时以 SessionStateUnknown 拒绝。后端一旦观察到锁屏或会话失效，解锁后仍须显式重新挂接。

终端任务管理

cargo run -p agent-cli -- task list --session SESSION_ID --page-size 100
cargo run -p agent-cli -- task get TASK_ID
cargo run -p agent-cli -- task reconcile TASK_ID --node-id WORKER_ID --node-endpoint https://worker.example:7448

task dispatch --help 列出派发参数。必须显式提供稳定的 Task UUID、Attempt UUID、幂等键及同一 Session 中正在运行的父 Run；daemon 校验所有权、工作区、截止时间与能力范围。task cancel 请求取消；task accept 必须使用 --accepted true 或 --accepted false 显式决定是否采纳 Worker 结果。

Browser 的连接、导航、关闭或接管请求尚未完成时，也必须等待结果才能切换、新建或关闭当前聊天，以及重新连接 daemon。Space 创建成功但地址打开失败时，界面保留该 Space，可修正地址后继续打开，或显式关闭。切换接管状态后，面板清除旧帧并重新获取；迟到的旧帧、空帧或错误不会覆盖新的读取状态。

Computer 面板

先连接 daemon 并选择已有聊天，再打开 Computer 面板：

  1. 选择 Refresh targets，读取本机目标目录。
  2. 在组件库提供的可搜索 Select 中明确选择窗口或显示器。刷新后的选择为空，不自动选中第一项。
  3. 选择 Attach to selected chat，将准确的目标描述符挂接到当前选定聊天。

连接节点与 Control Relay

本页面向配置 Master、Worker 和自托管 agent-control 的运维人员。直连与 Relay 共用 PeerService、TaskService、节点配对和任务持久化规则。客户端只连接本机 Master；跨节点连接由 daemon 建立。组件关系见组件与调用关系。

先确认身份与权限

每个 daemon 使用独立数据目录和节点身份。公开身份包含节点 ID、TLS 证书和 Noise 公钥；私钥保留在本机 peers/peer-identity.json。Control 使用自己的数据目录，在 identity/peer-identity.json 保存私有身份，在 control.sqlite3 保存信任、目录记录和允许转发的节点关系。只交换 peer-identity / identity 命令导出的公开 JSON，不复制私有身份文件。

配对前，通过独立可信渠道核对命令输出的完整配对指纹。指纹绑定节点 ID、TLS 证书指纹和 Noise 公钥；仅核对证书指纹不足以授权 Noise 身份。配对是本地人工操作；网络 Pair 接口拒绝修改信任，mDNS 候选也不会建立信任或选择路由。

在仓库根目录运行以下命令。将示例目录替换为实际绝对路径。daemon 维护命令需要独占数据目录，应先妥善停止对应 daemon，再操作并重启监听器以重新加载 mTLS 信任根。首次导出身份不要求开启 peer 监听器。

cargo run -p agentd -- --data-dir /path/to/master peer-identity > master-public.json
cargo run -p agentd -- --data-dir /path/to/worker peer-identity > worker-public.json

JSON 写到标准输出；完整配对指纹写到标准错误。以下命令中的 <verified-…-fingerprint> 必须替换为独立核对后的值：

cargo run -p agentd -- --data-dir /path/to/worker peer-pair \
  --identity master-public.json --fingerprint '<verified-master-fingerprint>' \
  --capabilities tasks.submit,tasks.read,tasks.cancel,tasks.accept,workspace.read,workspace.write.approval
cargo run -p agentd -- --data-dir /path/to/master peer-pair \
  --identity worker-public.json --fingerprint '<verified-worker-fingerprint>' \
  --capabilities workspace.read,workspace.write.approval

权限按接收方保存的信任记录判断：Worker 对 Master 授予 tasks.submit、tasks.read、tasks.cancel、tasks.accept，分别允许提交、查询/事件、取消和结果采纳。提交还要求 Master 的信任范围包含任务请求的每个能力。示例允许读和需审批的写；只需读取时，应同时从配对范围和任务范围移除 workspace.write.approval。Master 对 Worker 的配对用于验证 Worker 身份，不因此授予 Worker 反向提交任务的权限。

配置直连

在各 daemon 数据目录的 config.toml 加入：

[peer]
listen = "0.0.0.0:7448"
advertise_url = "https://worker.example.test:7448"
mdns = false

每个节点使用自己的可达地址。listen 端口必须非零；advertise_url 必须是 HTTPS origin，端口与监听端口相同，不能含凭证、路径、查询参数、fragment 或通配主机名。不能将未指定地址 0.0.0.0 / :: 用作公告地址。未配置 [peer] 时不会启动 peer 监听器；启动 mTLS 监听器前至少配对一个节点。

保留本地客户端的回环监听地址；不要把默认 127.0.0.1:7447 客户端入口开放到公网。peer 监听器单独提供 mTLS 的节点和任务服务。TLS 使用配对证书与节点派生的服务名验证身份，连接后 Hello 再核对节点 ID、证书指纹和协议范围。

daemon 的配置优先级见本地运行。peer 设置支持 LYONBROWN_PEER_LISTEN、LYONBROWN_PEER_ADVERTISE_URL、LYONBROWN_PEER_MDNS 环境变量；mdns 默认 false。启用发现仍需人工配对并显式提供目标。

配置出站 Relay

Master 和 Worker 都主动连接 Control 的 HTTPS 监听器，无需让另一节点直接访问本机 peer TCP 端口。每个 daemon 仍需配置 [peer]，启动时仍绑定该本地端口；仅使用 Relay 时可将 listen 绑定回环地址，advertise_url 仍须满足 peer URL 校验。

先导出 Control 公开身份：

cargo run -p agent-control -- --data-dir /path/to/control identity > control-public.json

在 Master 和 Worker 上分别导入已核验的 Control 身份。control.relay 是此配对的明确范围，不能代替 Master 与 Worker 之间的配对：

cargo run -p agentd -- --data-dir /path/to/master peer-pair \
  --identity control-public.json --fingerprint '<verified-control-fingerprint>' \
  --capabilities control.relay
cargo run -p agentd -- --data-dir /path/to/worker peer-pair \
  --identity control-public.json --fingerprint '<verified-control-fingerprint>' \
  --capabilities control.relay

Control 也要导入双方公开身份，并显式允许两个方向：

cargo run -p agent-control -- --data-dir /path/to/control pair master-public.json \
  --pairing-fingerprint '<verified-master-fingerprint>'
cargo run -p agent-control -- --data-dir /path/to/control pair worker-public.json \
  --pairing-fingerprint '<verified-worker-fingerprint>'
cargo run -p agent-control -- --data-dir /path/to/control allow '<master-node-id>' '<worker-node-id>'
cargo run -p agent-control -- --data-dir /path/to/control allow '<worker-node-id>' '<master-node-id>'

pair 在 Control 中授予 control.register、control.resolve、control.relay。allow 只授权一个方向，返回流量需要反向授权。配对后重启 Control 监听器以加载信任根。

在 Master 的 config.toml 加入以下内容，Worker 上则将 routes 改为 Master 的节点 ID。节点 ID 来自公开身份 JSON，不是目录名或自行选择的显示名称。

[relay]
control_node_id = "control"
endpoint = "https://control.example.test:7449"
routes = ["<worker-node-id>"]

routes 接受 1 至 32 个不同节点 ID，不能包含 Control 或本机 ID。Control ID 和路由 ID 只允许 ASCII 字母、数字、-、_、:、.，长度为 1 至 128。Relay endpoint 必须是无凭证、路径、查询参数或 fragment 的 HTTPS origin。Relay 设置由 TOML 提供，没有专用的 Relay 环境变量或 CLI 参数。

routes 中的节点始终使用 Relay；不在其中的节点走直连。选定 Relay 后，断线或认证失败会返回错误，不会自动改走直连。Task 命令仍需提供 Worker 的 HTTPS --node-endpoint，用于同一内层 mTLS 连接；此地址不会因 Relay 模式而变成 Control 地址。

Control 默认读取其数据目录中的 control.toml，或使用 --config 指定文件。例如：

node_id = "control"
listen = "0.0.0.0:7449"
lease_seconds = 60
queue_capacity = 32
log_directory = "logs"
log_retention = 14
log_filter = "info"

Control 按默认值、TOML、配置文件旁的 .env、进程环境、--listen 顺序覆盖。环境变量为 LYONBROWN_CONTROL_NODE_ID、LYONBROWN_CONTROL_LISTEN、LYONBROWN_CONTROL_LEASE_SECONDS、LYONBROWN_CONTROL_QUEUE_CAPACITY、LYONBROWN_CONTROL_LOG_DIRECTORY、LYONBROWN_CONTROL_LOG_RETENTION、LYONBROWN_CONTROL_LOG_FILTER。默认监听 127.0.0.1:7449；目录租期允许 1 至 3600 秒，队列容量允许 1 至 1024，日志保留文件数允许 1 至 365。相对日志目录以 Control 数据目录为基准。

也可在 control.toml 中使用 allowed_links = [] 或 [[allowed_links]] 的 source、target 字段管理关系。只要该字段存在，serve 启动时就会原子替换数据库中的整张允许关系表；省略该字段则保留 allow / deny 写入的关系。

cargo run -p agent-control -- --data-dir /path/to/control serve
cargo run -p agentd -- --data-dir /path/to/master
cargo run -p agentd -- --data-dir /path/to/worker

三条命令运行于各自节点或终端。Control 使用 mTLS 验证出站流身份，再按方向检查转发权限；Noise IK 使用配对公钥验证端到端隧道，隧道内仍运行普通 mTLS 与 TaskService。Control 可见源/目标节点、连接标识和密文长度，不接收任务明文，也不执行模型或工具。队列有界且不作为持久任务队列；接收或入队成功不等于 Worker 已执行。

ControlService 提供带租期的 Register / Resolve，但 daemon 的 Relay runtime 只建立出站流，不自动注册、续租或解析目录。此配置使用显式路由，不依赖目录注册；目录记录也不能建立配对信任。

派发、审批与断线恢复

通过连接 Master 的 CLI 管理任务。先在 Master 创建会话并启动运行；派发要求 --parent-run 是该会话中状态为 running 的运行。Task 与 Attempt 均使用预先保存的 UUID，idempotency_key 使用稳定标识。

cargo run -p agent-cli -- --data-dir /path/to/master task dispatch \
  --node-id '<worker-node-id>' --node-endpoint https://worker.example.test:7448 \
  --session '<session-id>' --parent-run '<active-run-id>' \
  --task-id '<task-uuid>' --attempt-id '<attempt-uuid>' \
  --idempotency-key '<stable-key>' --instructions 'Inspect the assigned workspace' \
  --capability workspace.read --deadline-seconds 3600

截止时间允许 1 至 86400 秒。Worker 使用自身模型、凭据与 Harness，在 worker-workspaces/<task_id>/<attempt_id> 下创建独立工作区和会话；不会复制 Master 的会话历史或工作区文件。任务能力只能缩小 Worker 可用工具范围；写操作仍需 Worker 本地审批，通过连接 Worker 的客户端处理，Relay 和 Master 的结果采纳均不能绕过工具审批。

Worker 成功后 Task 为 awaiting_acceptance，Master 显式采纳后才是 completed：

cargo run -p agent-cli -- --data-dir /path/to/master task get '<task-uuid>'
cargo run -p agent-cli -- --data-dir /path/to/master task reconcile '<task-uuid>' \
  --node-id '<worker-node-id>' --node-endpoint https://worker.example.test:7448
cargo run -p agent-cli -- --data-dir /path/to/master task accept '<task-uuid>' \
  --node-id '<worker-node-id>' --node-endpoint https://worker.example.test:7448 --accepted true

task list --session <session-id> 查询 Master 的分页记录；task cancel 使用与 reconcile 相同的目标参数。拒绝结果使用 task accept … --accepted false。

断线、超时或取消响应丢失后，先保留原 Task、Attempt、幂等键和目标，再用 get 查看本地状态，用 reconcile 核对同一次远端尝试。Master 将结果未知的尝试保存为 uncertain；Relay 重新连通只恢复传输，不自动核对业务状态或重放请求。不要换用新标识重新派发来规避未知结果。Worker 重启也会将未持久结束的尝试标记为未知，不重新执行。状态与审批细节见会话、任务与恢复。

撤销与排障

  • 禁止一个转发方向：agent-control --data-dir /path/to/control deny <source> <target>。需要双向隔离时分别禁止两个方向；若配置了 allowed_links，同时修改配置以免重启时恢复旧关系。
  • 撤销 Control 中的节点身份：agent-control --data-dir /path/to/control revoke <node-id>。活动流会重新检查信任；重启监听器以移除旧 CA 根。
  • 撤销 daemon 中的身份：停止对应 daemon，执行 agentd --data-dir /path/to/node peer-revoke --node-id <node-id>，再启动监听器。更换身份需要重新导出、独立核验并在相关接收方重新配对。
  • mTLS 失败时，核对公开身份、完整配对指纹、双方信任和监听器是否重启；不要通过关闭验证恢复连接。
  • Relay 不通时，核对两端出站连接、双方 routes、Control 的双向允许关系和已配对身份。target has no active outbound relay stream 表示目标没有活动流；背压错误表示有界队列未能及时接受数据。
  • 查看各数据目录下的结构化日志，关注 control.listen、control.relay、relay.transport 和任务 ID。日志用于定位连接与状态变化；不要把 token、私钥或完整任务明文加入排障材料。

原生桌面执行边界

CLI 与 Desktop 以默认关闭的 native-computer feature 转发启用 agent-computer-runtime/native。原生 SDK 通过显式 native feature 启用：agent-computer-runtime/native 同时启用 agent-computer/native，并提供 attach_native 工厂。默认构建保留协议、执行引擎和可注入的 attach_host，不引入截图与输入 SDK。daemon 使用这条默认依赖路径。

原生目标发现只读取元数据，不捕获像素或请求系统授权。发现前后均检查交互会话与已有屏幕权限；最小化和零尺寸目标被排除，目录超过 512 项则拒绝。目标标签去除控制字符并限制为 512 个字符；DesktopTarget 的 Debug 输出省略可能含私密内容的标签。窗口描述符保留进程 ID，挂接后按窗口 ID 与进程 ID 核对，拒绝将替换窗口当成原目标。标题与几何信息按新观察核对，不把旧目录当成当前画面。

agent-computer 封装屏幕观察、输入和桌面租约；agent-computer-runtime 在进程内保留准备好的操作，并按 daemon Session、Run 和 owner_epoch 校验调用归属。执行消息只引用原准备记录、动作标识和内容摘要，不能替换输入内容。等待审批后，Runtime 使用原租约和原观察限制重新观察；内容变化、租约失效或取消都会阻止输入。准备记录在刷新或输入前消耗，失败后也不能重放同一动作。

客户端库可通过 attach_native 将原生宿主嵌入客户端进程并连接 daemon。连接前先核对 daemon 节点及选定会话的归属；握手携带固定的桌面范围，daemon 再次校验身份，并记录会话的 owner_epoch。每个会话只允许一个宿主连接，模型工具固定本次连接代次，每次操作均在发送前和接收后核对 Run 状态及会话归属；重新连接不能替换运行已经选定的宿主。连接成功本身不授予截图或输入权限。

连接只允许一个待返回命令；同一连接代次的请求串行排队，续租不能抢占已派发命令。等待可取消，超过 35 秒则拒绝，派发前再次校验连接代次。daemon 按请求标识、宿主、连接代次、Session、owner_epoch、私有协议版本和预期响应类型校验返回值，并检查租约、观察范围与图像、窗口、AX 节点边界。非法响应或断线会取消连接，不自动重放输入。原生调用和消息编解码在阻塞线程执行。已经进入操作系统的调用仍需实际结束；取消不会强行终止线程。原生宿主使用用户数据目录中的文件锁，按操作系统图形会话互斥，改变 daemon 节点标识或客户端数据目录不能绕过这把锁。执行线程持有文件锁至调用结束。

同进程的原生 Runtime 共享桌面租约注册表。按令牌撤销时，注册表在同一锁内校验并取消准确令牌，过期控制者不能撤销替代租约。私有 postcard 协议版本为 2，包含准确令牌的 RenewLease。续租只延长当前未撤销、未过期的令牌，不能取得新令牌或恢复旧控制权。消息总上限为 68 MiB，以容纳最多 64 MiB 的 RGBA 图像和元数据；超长帧前缀在分配载荷前拒绝。daemon 将能力响应限制为 4 KiB、观察响应限制为 68 MiB、其他响应与请求限制为 16 KiB。持久审批、执行意图和进程重启后的去重仍由 daemon 管理，进程内记录不能代替持久记录。

daemon 已通过这条认证连接装配 Harness 的 computer_observe 与 computer_act，启用条件、准确审批和持久回执见本地工具与浏览器操作。CLI/TUI 与 Desktop 已提供显式目标选择和会话连接入口，见原生计算机连接；配置开关本身不能建立原生宿主。这些组件不构成客户端到 Harness 的原生控制验收。macOS 会话检查与限制见下文。Windows 与 Linux 适配同样需要对应平台的权限；两平台的实际运行验收尚未完成。

macOS 通过 CoreGraphics 读取调用进程的会话，要求位于控制台、登录完成，且 CGSSessionUniqueSessionUUID 能解析为非全零 UUID。检查还通过维护中的 objc2 绑定读取 IORegistry 根节点，要求 IOConsoleLocked 明确为 false；它与 CGSSessionScreenIsLocked 任一为 true 时返回 Locked。IOConsoleLocked 缺失或类型错误、会话 UUID 缺失或无效时返回 SessionStateUnknown。会话检查前后各读取一次快照并校验；快照变化时拒绝。锁字段属于 macOS 的实际实现字段，以上为项目采用的兼容策略，不是 Apple 文档承诺的锁屏状态保证。

原生后端一旦观察到锁屏、无法读取的会话状态或会话身份变化，就保持撤销状态；解锁后同一后端也不会恢复控制，必须重新显式挂接。会话检查、屏幕捕获和输入仍是分开的操作系统调用，前后校验不构成原子性的捕获与输入保证。实现见 crates/agent-computer/src/native/macos.rs、session.rs 与 mod.rs。

开发与验证

工作区使用 Rust 2024 edition，产品依赖由 Cargo workspace 与 Cargo.lock 管理。Rust 工具链最低版本见根 Cargo.toml 的 rust-version。工程约束统一维护在根 AGENTS.md。

异步入口优先使用 #[tokio::main]，参数解析、序列化和依赖注入复用 Clap、Serde、fluxdi 的宏。CEF helper 和 Windows SCM 先完成平台分派；GPUI 保留主线程事件循环，需要持有或共享的运行时显式装配。

本地开发启动

仓库的 .cargo/config.toml 定义了 dev 别名，直接使用 Cargo，无需安装额外任务工具。在仓库根目录执行一条命令，自动构建、启动开发 agentd 并打开客户端：

cargo dev desktop
# 或启动终端界面
cargo dev tui

可以在不同终端多次执行 cargo dev tui，同时打开 Desktop。使用相同数据目录、地址和配置的客户端共用一个开发 agentd；命令自动传入连接地址和认证信息，无需先手动启动 daemon。

默认数据目录为 .local/dev/agentd，地址为 http://127.0.0.1:7547。开发目录在 cargo clean 后保留。命令使用前台开发进程，不注册或替换操作系统服务。首次启动 daemon 的终端保留其监督进程；关闭该终端中的客户端后，daemon 继续运行。在这个终端按 Ctrl+C 停止开发 daemon。后续终端只复用 daemon，退出客户端不会停止 daemon。

启动时会串行检查同一数据目录，避免多个客户端同时创建 daemon。复用前通过认证握手检查节点身份、协议、构建和配置。端口被其他进程占用、凭据不匹配或已有 daemon 与本次构建、配置不一致时，命令报错并保留已有进程。需要使用新构建或配置时，先在原终端停止开发 daemon，再重新执行启动命令。

路径相对于仓库根目录解析，可包含空格。多个客户端应使用相同参数；开发端口必须是非零回环端口，且不能使用产品默认端口 7447：

cargo dev desktop --dry-run
cargo dev tui --data-dir .local/dev/demo --listen 127.0.0.1:7548 --config /absolute/path/dev.toml
cargo dev desktop --data-dir .local/dev/demo --listen 127.0.0.1:7548 --config /absolute/path/dev.toml
cargo dev --help

Cargo 别名使用参数数组调用 apps/agent-dev，不依赖平台 Shell，也无需安装额外的任务运行器。根 README.md 列出常用命令，cargo --list 也会展示 dev 别名。

cargo dev tui 等价于 cargo run --locked -p agent-dev -- tui。首次执行时，Cargo 按 Cargo.lock 下载并编译 Rust 依赖，无需通过 cargo install 安装开发启动器、just 或 cargo-make。GPUI 和可选原生 SDK 所需的平台构建依赖仍需准备，见本地分发说明。

需要单独运行前台 daemon 时，使用 cargo dev daemon。其他开发客户端仍可自动连接并复用它。

默认配置为开发数据目录中的 config.toml，dotenv 文件位于配置文件旁边。--config 选择已有 TOML 文件；命令不创建或覆盖配置和 dotenv。模型、工具和日志使用共享 agent-config 的分层规则。agentd、TUI、Desktop 和开发启动器都通过共享 agent-telemetry 写入日志；默认位于开发数据目录的 logs 子目录，按进程前缀区分，并沿用配置中的滚动保留规则。启动命令强制使用所选开发地址和数据目录，并从该目录读取 auth.token，忽略继承的连接凭据。token 仅通过客户端子进程环境传递，不写入命令参数或启动输出。

--dry-run 展示启动方案，不创建目录、不读取 token、不启动产品进程；外层 Cargo 仍可能编译 agent-dev。默认 Desktop/TUI 构建不启用 native-cef 或 native-computer，对应的浏览器执行或原生计算机宿主能力会报告不可用。完整 CEF SDK、helper 和应用包布局见 本地分发说明。

原生计算机客户端构建

CLI 与 Desktop 的 native-computer feature 默认关闭，显式转发到 agent-computer-runtime/native，再启用 agent-computer/native。cargo dev desktop 和 cargo dev tui 的默认构建不自动启用它；native-cef 也不会启用原生计算机能力。开发启动器支持显式启用客户端 feature：

cargo dev desktop --native-computer
cargo dev tui --native-computer
cargo dev desktop --native-computer --dry-run

该参数只转发到客户端构建，不传给 agentd，也不修改 computer_tools 配置；cargo dev daemon --native-computer 会拒绝。也可以单独构建和启动客户端：

cargo build -p agent-cli -p agent-desktop --features agent-cli/native-computer,agent-desktop/native-computer --locked
cargo run -p agent-cli --features native-computer -- computer targets
cargo run -p agent-desktop --features native-computer

客户端通过共享 launcher 连接或复用原生 daemon 服务；开发前台 daemon 的使用方式见上方。原生 feature 不改变 daemon 的 computer_tools = false 默认值，也不代替系统权限、交互会话检查或准确动作审批。默认依赖和测试依赖均不通过 Cargo feature 合并隐式启用原生 SDK。目标选择、会话挂接和断开操作见终端与桌面客户端。

构建通过只说明对应主机上的代码可编译。原生目标发现、GUI 选择、客户端到 Harness 的连接、屏幕观察与获批输入均需实际运行验收。macOS 按会话身份与锁字段策略检查，无法确认状态时返回 SessionStateUnknown；不得将只读权限检查、拒绝路径或合成宿主回归称为原生控制验收。真实捕获、获批输入、锁屏与会话切换仍需实际验收；Windows 和 Linux 的实际运行验收也尚未完成。

原生服务验收

macOS 的以下测试使用真实 launchd 注册，只能在没有 Lyonbrown 服务注册且 127.0.0.1:7447 空闲的测试账号上执行。先构建产品 daemon，再提供其绝对路径：

cargo build -p agentd --bin agentd --locked
LYONBROWN_SERVICE_AGENTD=/absolute/path/agentd cargo test -p agent-launch --test native_service --locked -- --ignored --nocapture --test-threads=1

测试检查两个客户端复用同一服务、不同数据目录不能替换服务，以及原生服务重启后节点身份和会话记录保持一致。成功后会验证注册归属和空闲状态，再移除本次服务与测试数据。失败时保留数据，避免删除仍在运行的 daemon；先核对 service.json 与原生服务状态，再处理遗留注册。

此路径已在 macOS 27.0.1、arm64 上通过实际产品二进制验收，不涉及模型调用或钥匙串授权。它不替代 PKG 的操作系统安装验收，也不证明 Windows SCM 或 Linux systemd 的运行行为。
