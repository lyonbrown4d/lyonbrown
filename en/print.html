Lyonbrown User and Developer Guide

Overview

Lyonbrown keeps agent execution in the persistent agentd process. The terminal client and GPUI desktop access sessions, tasks and events through an authenticated protocol. Clients own input, presentation and connection state. Closing a window does not issue a task cancellation.

This guide is for local users and developers and describes the current Rust workspace. Start with Run locally, or read Sessions, tasks and recovery for execution and recovery semantics. Source behavior described here does not establish runtime acceptance for real models, native SDKs or cross-device operation.

Run locally

Install the Rust toolchain required by the root Cargo.toml. Models, native graphics and browser SDK prerequisites depend on enabled capabilities; a crate name does not establish availability without the relevant native dependencies.

Start the development environment

Choose a client with Cargo from the repository root. No additional task runner is required:

cargo dev tui
# Or open the desktop client:
cargo dev desktop

The command builds the required binaries, starts or reuses a development agentd and supplies the client connection settings. Multiple terminals and Desktop can share the default .local/dev/agentd data directory and 127.0.0.1:7547 endpoint. See Development and verification for data, configuration and shutdown options.

Run the daemon independently

Run from the repository root:

cargo run -p agentd -- --data-dir /path/to/lyonbrown-data

The default listener is 127.0.0.1:7447; the local client endpoint accepts loopback addresses only. The daemon stores node identity, auth.token and agent.sqlite3 in the data directory and holds an exclusive lease on it. A second daemon using the same directory fails, preventing concurrent node-state writers.

Model requests originate in the daemon. Set OPENAI_API_KEY through the process environment or a .env adjacent to the configuration file before startup; use ANTHROPIC_API_KEY with the anthropic provider. Do not commit real credentials. Real-model requests cannot execute without provider credentials.

The shared agent-config uses config and dotenvy. Configuration merges defaults, TOML, the .env adjacent to that file, process environment and explicit CLI arguments in that order. The default file is config.toml in the data directory; --config-file or LYONBROWN_CONFIG selects another file. Dotenv parsing does not mutate the global process environment. Provider endpoints require HTTPS, with HTTP allowed for loopback addresses. URLs cannot contain credentials, query parameters or fragments. The API mode must match the endpoint.

supports_images defaults to false. Enable --supports-images or LYONBROWN_SUPPORTS_IMAGES=true only when both provider and model support image inputs. See Models and execution decisions for classification settings, a TOML example and protocol mappings.

Files rotate daily, retaining 14 files per process prefix. LYONBROWN_LOG_DIRECTORY and LYONBROWN_LOG_RETENTION override these settings; retention accepts 1..=365. Credentials stay out of UI models and configuration debug output.

Run clients directly and use native services

For development, cargo dev tui or cargo dev desktop automatically starts and connects to the shared development daemon. See Development and verification for options. Installed terminal and Desktop clients use the shared launcher at the default local endpoint to reuse the same user’s native service after checking version, protocol and capabilities. macOS uses launchd, Linux uses a systemd user service, and Windows uses an SCM identity derived from the current user’s SID.

The service registration lock and service.json always live in the default user data directory, regardless of a client’s --data-dir. If an existing service uses a different data directory, the launcher refuses replacement; changing the client directory cannot register a second service with the same identity. The authentication token remains in the daemon’s actual data directory.

On Windows, install the MSI, then select Set up Lyonbrown service in the Start menu. Setup requires same-account UAC elevation and collects the service login password in the native credential dialog; switching to another administrator account is rejected. CLI and Desktop share a protected Program Files daemon. Passwords never enter command-line arguments or configuration files. Upgrades wait for active tasks and check storage compatibility and rollback conditions.

Using cargo run to connect to the default local endpoint also checks the native service, so it requires the complete installed daemon or a built agentd beside the client binary. Prefer the cargo dev commands above during development. To run the terminal directly:

cargo run -p agent-cli -- --endpoint http://127.0.0.1:7447 --data-dir /path/to/lyonbrown-data

Clients receive tokens through --token, LYONBROWN_TOKEN or the adjacent dotenv file. At the default local endpoint, the shared launcher reads auth.token from the reused daemon’s data directory; other endpoints require an explicit token. Keep tokens out of documentation, Git and chat history. Environment variables or local files avoid placing the value in command history.

Models and execution decisions

Each run receives an execution plan from agent-decision before agent-runtime opens rpi-harness. A classifier returns advice. It executes no tools and cannot grant permissions.

How the plan controls execution

Without decision.model, the daemon uses an explicit workspace rule: the general model policy, read_file and write_file, with MCP, browser and trusted-command tools selected by configuration and available runtime capabilities. Configured, actively paired delegation targets can enable distributed execution and delegate_task. Workspace path restrictions and per-operation mutation approval still apply. This rule comes from daemon policy; prompt text cannot supply authorization.

When configured, the classifier receives the user request as data. It must return one JSON object containing task_kind, model_policy, allowed_tools, execution_mode, target_hint, risk_level and confidence. Unknown fields, invalid enums, wrong types and confidence outside the allowed range are rejected.

The tool set is the intersection of the classifier’s selection, authorized tools and available capabilities. Model policies, distributed execution and target nodes are independently constrained by allowlists. Delegation targets must appear in both operator configuration and active pairing records. Local plans do not expose delegation. Classifier output cannot widen tool, model or node authority. See Delegating to paired nodes for configuration and approval scope.

The effective plan is persisted as an execution_plan event before opening the Harness. It records tools, capabilities, execution mode, risk, confidence, source and trace_id. The daemon filters the actual Harness tools against this plan, restricting both model-visible tools and execution. Approval consumption checks the run, tool, full arguments and expiry; a classification never replaces human approval.

Unavailable classifiers, timeout, invalid output, insufficient confidence or missing required capabilities fall back to a local general model with no tools or target node. Cancellation during classification persists a cancelled run without calling the main model.

Local inference boundary

agent-inference adapts llama-cpp-2 and mistral.rs. Both generate model output; the same rpi-harness retains session and loop ownership. The daemon loads configured local files into its registry before becoming ready. Load failure prevents startup without downloading models or falling back to a cloud provider.

provider = "local"
model = "local-main"

[[local_models]]
id = "local-main"
backend = "llama"
format = "gguf"
path = "/absolute/path/to/chat-model.gguf"
context_window = 4096
max_output_tokens = 512
parallel_requests = 1
max_model_bytes = 8589934592

Replace the example path with an existing local model. Windows requires a native absolute path. Build agentd with local-llama for llama, or local-mistral for mistral. Llama reads GGUF; Mistral accepts gguf or directory. The selected engine must support the actual model architecture and quantization; a matching extension alone does not establish compatibility.

Profiles explicitly select CPU execution without implicit GPU allocation. max_model_bytes bounds input file size, rather than runtime RAM. Context, output tokens and concurrency have separate limits. Each run persists actual metadata in model_selected. Text-only backends do not advertise image or tool support; the daemon removes unsupported tools before persisting the effective plan and opening the Harness.

To select a local classifier independently, set decision.provider = "local" and point decision.model to a configured profile ID. LocalClassifier accepts structured output without tool calls and applies the same JSON, confidence, deadline and cancellation checks. Invalid output takes the conservative fallback. A local main model needs no cloud credentials.

Connect MCP tools

agentd uses rmcp to connect to explicitly configured MCP servers over stdio or Streamable HTTP. The daemon owns connections and cached tool catalogs. Clients present approvals and results; model input cannot add servers or alter transports.

Servers and credentials

List servers and allowed tools in the shared data directory’s config.toml:

[[mcp]]
id = "reference"
allowed_tools = ["lookup"]

[mcp.transport]
type = "streamable_http"
url = "https://mcp.example.com/rpc"
headers = { Authorization = "MCP_AUTHORIZATION" }

The endpoint and tool name are examples and must match the real server. Header values name environment variables. Set each variable in the adjacent .env or process environment to the complete header value required by the server, such as Bearer .... Process values override dotenv values. A missing reference prevents startup. Credentials do not enter model tool schemas or approval arguments.

Remote HTTP servers require HTTPS; plain HTTP is limited to loopback addresses. URLs cannot include credentials, queries or fragments. The HTTP client neither follows redirects nor inherits proxy environment settings.

Local processes require an absolute executable path:

[[mcp]]
id = "local-reference"
allowed_tools = ["lookup"]

[mcp.transport]
type = "stdio"
executable = "/absolute/path/to/mcp-server"
arguments = ["--stdio"]
environment = { SERVER_TOKEN = "LOCAL_MCP_TOKEN" }

The path example is for macOS/Linux. On Windows, use a native absolute path; TOML single-quoted strings preserve backslashes. Each environment entry maps a child variable to a dotenv/process variable name. Only explicit references and a small set of operating-system variables reach the child, rather than the full parent environment or implicit model credentials. Bounded stderr diagnostics are retained in the private log directory.

Configuration permits at most 64 servers and 64 selected tools in total. Every allowed tool must exist in the returned catalog and provide a supported, bounded object schema. External schema references are rejected.

Invocation and approval

Models invoke selected tools through mcp_call. The server, tool and arguments inside call must match the same catalog branch:

{
  "call": {
    "server": "reference",
    "tool": "lookup",
    "arguments": { "query": "example" }
  }
}

These arguments are illustrative; the selected server’s schema determines the real fields. Nesting the complete branch inside a root property preserves the identity/schema association through all three model protocol adapters. Server descriptions and results remain untrusted data.

The daemon validates the allowlist and schema before persisting approval. Approval binds the Run, server, tool, call ID, exact arguments and expiry; it can be consumed once, before dispatch. Read-only annotations and classifier confidence do not waive approval. Without configured MCP servers, mcp_call appears in neither the effective plan nor the model’s tools. Classification can only reduce that authority.

Cancellation before dispatch sends no tool invocation. Cancellation, timeout or disconnection after dispatch may leave unknown side effects. Such runs become Uncertain and are never automatically replayed. Pending approvals close when the run ends; consumed approvals retain their record. See Sessions, tasks and recovery.

Returned resource links are not fetched automatically. Sampling and elicitation cannot expand client authority. Protocol messages, text and image outputs have size limits. Daemon shutdown cancels shared connections; retained run tools cannot issue later requests.

Source: crates/agent-mcp, crates/agent-config/src/mcp.rs, apps/agentd/src/mcp.rs and apps/agentd/src/authorization.rs.

Local tools and browser actions

agentd assembles model tools; clients display calls, approvals and results. Tool results, page content and process output cannot grant additional authority. A remote session’s native commands execute on the daemon host.

Enable trusted commands

execute_command is disabled by default. An operator explicitly lists absolute executable paths in the daemon’s config.toml; restart the daemon to expose the tool. This macOS example allows /usr/bin/printf and passes only the selected environment reference to the child:

[commands]
executables = ["/usr/bin/printf"]

[commands.environment]
CHILD_KEY = "LYONBROWN_CHILD_VALUE"

LYONBROWN_CHILD_VALUE must exist in the dotenv or process environment read by layered configuration. The right-hand side names a variable rather than containing a credential. Unresolved references fail configuration loading. Children do not inherit the full environment. Arguments go directly to the executable without a shell. Executable and environment maps each allow up to 64 entries.

The working directory must remain inside the session workspace and defaults to .. This does not isolate filesystem or network access: a trusted program retains the operating-system rights of the user running agentd. Allowing an interpreter or shell permits its arguments to express broader actions; operators must assess the program and each exact argument list.

Model browser tools

browser_observe lists the current session’s tabs or observes a selected tab, returning its snapshot, revision, accessibility data and optional screenshot artifact reference. Content is marked untrusted. Tab-list URLs omit queries and fragments; page text cannot act as system authorization.

browser_act takes a call object and supports:

OperationRequired conditions
open_spaceprofile_id and an attached runtime host; optional host_id and headless
open_tabA space_id in this session and an allowed URL
close_spaceA space_id in this session
click / fill / presstab_id, current snapshot_id, revision and an observed element_ref
navigatetab_id, current snapshot_id, revision and the destination URL in text

Mutations require exact-action human approval. The daemon checks the session, owner epoch, runtime host binding, cancellation and human takeover state. Human takeover suspends model mutations; model tools expose neither raw input nor takeover. Observe again after a stale snapshot. Inspect recorded outcomes before proceeding after uncertainty; automatic replay is forbidden. Profile persistence does not establish live-page recovery.

For model mutations, one local transaction consumes the exact approval, records browser intent, and writes events and Outbox. It rechecks that the run is executing and the session and owner epoch match. A failed transaction rolls back approval consumption and intent together. Only after commit is the command sent to the approved runtime host. Cancellation or disconnection while awaiting a receipt preserves Uncertain without replay. Human browser commands use a separate authenticated entry point and record the same kinds of intent and outcome receipts.

Native CEF semantic actions invalidate the old snapshot before scrolling, focusing, key input or navigation. After entering these steps, an action error or failed follow-up observation produces Uncertain, stops the current model Run and retains durable receipts for human reconciliation. Input, ownership and snapshot checks precede the action.

Human takeover input invalidates cached semantic observations before focus or dispatch. Errors after that boundary produce a durable Uncertain receipt without automatic replay. Successful input does not itself advance the frame revision, preserving paired down/up events; page changes may still invalidate that revision.

apps/agentd/tests/browser_tools.rs uses local HTTP model mocks and real protocol adapters for Responses, Chat Completions and Anthropic Messages. It covers approval, denial, ownership/session boundaries, cancellation and screenshot artifacts. Its runtime host is synthetic: it verifies the Harness-to-daemon tool contract and durable state, and does not replace autonomous browser acceptance with native CEF.

apps/agentd/tests/native_browser_tools.rs separately verifies the native chain. In a debug CEF environment on macOS 27.0.1 arm64, all three protocols completed real AX observation, exactly approved fill and click actions, local HTTP page effects and durable receipts. Three additional scenarios discarded the receipt after an actual successful click; cancellation and recovery preserved Uncertain without replay. The test uses synthetic pages, isolated profiles and the debug test keychain. It does not establish production keychain or other-platform acceptance.

apps/agentd/tests/native_browser_post_effect.rs verifies a post-click page error through the Responses protocol: one actual click produces one local HTTP effect, followed by an error from oversized page content. It checks durable Uncertain Run and browser receipts, stopped model continuation, recovery without replay and rejection of new Runs in the unresolved session. This case and the six scenarios above ran against a rebuilt and signed native host.

The same debug environment also passed apps/agentd/tests/native_browser_human_input.rs: paired human mouse input produced one page effect, persisted an uncertain receipt and matching Outbox, and recovered without replay or model execution. crates/agent-browser-runtime/tests/cef_runtime.rs verifies successful same-revision pointer input and committed text.

Model computer tools

computer_observe and computer_act are disabled by default. Trusted daemon configuration enables them with top-level computer_tools = true, or LYONBROWN_COMPUTER_TOOLS. computer_lease_secs defaults to 300 seconds and accepts 10..=300; its environment variable is LYONBROWN_COMPUTER_LEASE_SECS. Both use shared configuration layering. These switches do not create a native attachment. CLI/TUI and Desktop require explicit target selection and session attachment; see terminal and desktop clients.

Before advertising computer capability to the decision model, the daemon requires an authenticated host with a fixed desktop scope bound to the same owned Session and owner_epoch, plus a capability reply whose can_control() is true. Attachment, model selection or configuration alone cannot bypass screen and input permission checks. The sole Harness executes these tools without a separate Agent Loop.

computer_observe accepts optional screenshot (default false) and returns snapshot_id, revision, scope, windows and bounded AX semantics, marked untrusted_desktop_content. Semantic output is limited to 1 MiB. Requested screenshots are encoded as PNG artifacts and returned as digests, without raw RGBA pixels in model text. Desktop content cannot grant authority.

computer_act requires the last observation’s snapshot_id, revision and one action: move, click, scroll, key or text. timeout_ms defaults to 5000 and accepts 1..=30000 milliseconds. Each call consumes the observation reference, captures again and compares the original content digest. Content changes during model latency require another observation; the tool cannot silently adopt a new screen. Matching content produces an immutable preparation retained by the runtime.

Human approval binds the action, host, Session, owner_epoch, Run, model call, original observation reference, complete preparation and timeout. In one local transaction, the daemon consumes that exact approval and records the execution intent, events and Outbox before sending Execute. Before input, the runtime captures again using the original lease and limits. Changed content, an invalid lease or cancellation prevents input; failed preparations cannot be replayed. A committed action’s actual reply becomes a durable receipt. Cancellation, disconnection, invalid receipts or unknown outcomes enter Uncertain, stop continuation and require verification without automatic replay.

A Run-scoped keeper renews the current live token during model generation and approval waits, attempting renewal every third of the lease period. It cannot revive an expired or revoked controller. Run closure stops renewal and revokes the exact token, disconnecting the pinned attachment if revocation fails. See protocol and platform capabilities for authentication, transport limits and platform restrictions.

Sources: apps/agentd/src/computer/tools/, apps/agentd/src/computer/mutation.rs, apps/agentd/src/execution.rs and crates/agent-computer-runtime/src/. See development and verification for synthetic-host regression coverage; it does not replace native desktop acceptance.

Delegating to paired nodes

delegate_task is disabled by default. Verify the complete TLS and Noise pairing fingerprint through the daemon’s peer-pair operation, then list the permitted node, HTTPS origin and capabilities in config.toml. Discovery results and model output cannot create pairings or change target origins.

[[delegation_targets]]
node_id = "worker-example"
endpoint = "https://worker.example:7448"
capabilities = ["workspace.read"]

This declares a permitted route; it neither creates trust nor expands the durable pairing grant. Supported capabilities are workspace.read and workspace.write.approval, further restricted by the effective execution plan. Only plans permitting distributed execution expose this tool to the Harness. Worker child runs cannot delegate again.

The model selects dispatch, get, reconcile, cancel or accept inside call. A task must belong to the current parent Run, Session, owner and owner_epoch. Dispatch specifies the target, instructions, capabilities and timeout. The daemon derives stable task and attempt identities from the current model call so repeated calls cannot start another execution.

Dispatch, cancellation and result acceptance require separate exact-action approvals. Dispatch approval binds the origin, complete paired identity and task scope. Acceptance also binds the reconciled result’s SHA-256 digest and content. Changes to pairing, Session ownership or the result invalidate an earlier approval. Worker content is always untrusted and cannot grant authority.

After durable intent exists, disconnection, cancellation or a lost receipt produces Uncertain and stops the Run for reconciliation of that identity. Reconciliation queries the existing task without dispatching it again. See Clients for human management commands.

apps/agentd/tests/delegation.rs uses actual adapters for all three model protocols, local model mocks and both Master and paired mTLS Worker Harnesses. It covers dispatch, approvals and result acceptance, as well as denial, revocation, rekeying, cross-parent access, scope expansion and unknown outcomes without replay.

Components and calls

agentd owns sessions, tasks, models, tools and permissions. agent-client puts a bearer token in gRPC request metadata; terminal and desktop clients use the same ClientService messages. Concrete rpi-harness types stay within the runtime adapter and do not enter public protocol or UI models.

Remote model protocols, local inference engines and decision classifiers share domain boundaries. Model metadata determines tool, image and context support. Sessions, tasks and recovery

Sessions preserve the Harness semantics needed to continue a conversation. Run records preserve orchestration state for individual user requests. SQLite stores these separately and writes events and outbox records alongside critical changes.

Images in snapshots and events

Harness snapshots retain original message content. The separate entry_appended and record_appended projections retain only type, mimeType, dataRedacted and encodedBytes for image blocks, without Base64 content. encodedBytes is the byte length of the original Base64 string. This applies to tool results, compaction tails, execution intents, queued messages and stream-start messages. Store, Outbox and WatchRun carry the same projected payload. Projection happens when Runtime commits new events; reading existing events does not recompute their payloads.

Projection follows known message schemas rather than recursively removing arbitrary JSON data fields. Tool arguments and custom business data remain the responsibility of their adapters. Unrecognized queue payloads or frames expose only a projectionOmitted marker. Input-image Debug output includes only MIME and length.

Image-bearing session recovery is unavailable. The recovery entry point retains the snapshot and returns an explicit error without calling a model or replaying a request. rpi-ai 0.5.0 emits duplicate type keys in raw JSON serialization; see upstream issue #59. No snapshot normalization workaround is included. The daemon’s StartRun still accepts text only; internal Runtime image input does not establish client image-session support.

Disconnection and restart

After reconnecting, query runs in the original session. Events are ordered by run ID and cursor; WatchRun.after_cursor requests later events. A disconnected stream does not establish task failure and must not trigger prompt replay.

The store’s recover_interrupted marks executing records without a durable terminal result as uncertain. Accepted work that has not started is handled separately from work already executing. Runtime recovery checks unfinished Harness tool records: a missing committed tool result produces Uncertain instead of guessing whether the side effect happened.

The same recovery transaction changes the run’s pending approvals to cancelled and writes approval_closed, run_uncertain events and Outbox entries. If any write fails, these state and event changes roll back together; repeated recovery creates no additional records. Closing an old approval neither resolves an unknown run outcome nor authorizes tool replay.

An uncertain run remains unresolved. Starting another run in the same session cannot bypass it. Preserve the database, events and external operation evidence, then reconcile the actual outcome before choosing the next action. The current protocol has no general-purpose endpoint for manually changing terminal state.

Approvals

An approval records the tool, arguments, owning run and expiry. decide_approval accepts only unexpired requests whose run is still awaiting approval. Consumption rechecks the run, tool and arguments and changes the approval to consumed, preventing reuse of the same authorization.

Master and worker

TaskStore checks attempt_id and owner_epoch when updating worker attempts or accepting results. A successful attempt first enters awaiting_acceptance; a task becomes completed only after explicit result acceptance.

Worker startup recovery marks only accepted or running attempts whose persisted dispatch target is the local node as uncertain, preserving ownership checks. Master records dispatched to other nodes and generic tasks without a target remain unchanged. This routine neither transfers Master ownership nor replays attempts.

Connect peers and Control Relay

This page is for operators configuring a Master, Worker and self-hosted agent-control. Direct connections and Relay use the same PeerService, TaskService, pairing and durable task rules. Clients connect to their local Master; daemons establish connections between nodes. See Components and calls.

Verify identities and permissions

Each daemon has its own data directory and node identity. Its public identity contains a node ID, TLS certificate and Noise public key. Private keys stay in its local peers/peer-identity.json. Control has a separate data directory: identity/peer-identity.json holds its private identity, while control.sqlite3 holds trust, directory records and allowed links. Exchange only public JSON exported by the identity commands below; do not copy private identity files.

Before pairing, compare the complete pairing fingerprint over an independent trusted channel. It binds the node ID, TLS certificate fingerprint and Noise public key. A certificate-only fingerprint cannot authorize the independent Noise identity. Pairing is a local human action: network Pair requests are denied, and mDNS candidates neither establish trust nor select routes.

Run commands from the repository root, replacing example directories with actual absolute paths. Daemon maintenance commands require exclusive access to their data directory. Stop the corresponding daemon safely before maintenance, then restart its listener to reload mTLS trust roots. Initial identity export does not require a peer listener.

cargo run -p agentd -- --data-dir /path/to/master peer-identity > master-public.json
cargo run -p agentd -- --data-dir /path/to/worker peer-identity > worker-public.json

Public JSON goes to stdout; the complete pairing fingerprint goes to stderr. Replace the fingerprint placeholders only after independent verification:

cargo run -p agentd -- --data-dir /path/to/worker peer-pair \
  --identity master-public.json --fingerprint '<verified-master-fingerprint>' \
  --capabilities tasks.submit,tasks.read,tasks.cancel,tasks.accept,workspace.read,workspace.write.approval
cargo run -p agentd -- --data-dir /path/to/master peer-pair \
  --identity worker-public.json --fingerprint '<verified-worker-fingerprint>' \
  --capabilities workspace.read,workspace.write.approval

The receiving node’s trust record governs permissions. On the Worker, tasks.submit, tasks.read, tasks.cancel and tasks.accept allow the Master to submit, query/watch, cancel and accept results respectively. Submission also requires the Master’s trust scope to include every requested task capability. This example permits reads and writes requiring approval; for read-only work, remove workspace.write.approval from both the pairing and task scopes. Pairing the Worker on the Master verifies the Worker’s identity without granting it reverse task-submission permission.

Configure direct connections

Add this section to each daemon’s config.toml in its data directory:

[peer]
listen = "0.0.0.0:7448"
advertise_url = "https://worker.example.test:7448"
mdns = false

Use each node’s own reachable address. The listen port must be nonzero. advertise_url must be an HTTPS origin using that port, without credentials, a path, query, fragment or wildcard hostname. Unspecified addresses 0.0.0.0 / :: cannot be advertised. Without [peer], no peer listener starts. Pair at least one node before starting an mTLS listener.

Keep the local client listener on loopback; do not expose the default client endpoint 127.0.0.1:7447 publicly. The separate peer listener provides mTLS node and task services. TLS verifies the paired certificate and node-derived server name; Hello then checks the node ID, certificate fingerprint and protocol range.

See Run locally for daemon configuration precedence. Peer settings support LYONBROWN_PEER_LISTEN, LYONBROWN_PEER_ADVERTISE_URL and LYONBROWN_PEER_MDNS. mdns defaults to false; enabling it still requires human pairing and an explicit target.

Configure outbound Relay

Both Master and Worker initiate connections to Control’s HTTPS listener. Neither needs direct access to the other’s peer TCP port. Both still require [peer] and bind its local port at startup. For Relay-only operation, listen may use loopback; advertise_url must still satisfy peer URL validation.

Export Control’s public identity:

cargo run -p agent-control -- --data-dir /path/to/control identity > control-public.json

Import its verified identity on both daemons. The explicit control.relay scope does not replace pairing between Master and Worker:

cargo run -p agentd -- --data-dir /path/to/master peer-pair \
  --identity control-public.json --fingerprint '<verified-control-fingerprint>' \
  --capabilities control.relay
cargo run -p agentd -- --data-dir /path/to/worker peer-pair \
  --identity control-public.json --fingerprint '<verified-control-fingerprint>' \
  --capabilities control.relay

Import both public identities on Control and authorize both directions:

cargo run -p agent-control -- --data-dir /path/to/control pair master-public.json \
  --pairing-fingerprint '<verified-master-fingerprint>'
cargo run -p agent-control -- --data-dir /path/to/control pair worker-public.json \
  --pairing-fingerprint '<verified-worker-fingerprint>'
cargo run -p agent-control -- --data-dir /path/to/control allow '<master-node-id>' '<worker-node-id>'
cargo run -p agent-control -- --data-dir /path/to/control allow '<worker-node-id>' '<master-node-id>'

Control’s pair grants control.register, control.resolve and control.relay. allow authorizes one direction only; responses require the reverse direction. Restart Control’s listener after pairing to load its trust roots.

Add this section to the Master’s config.toml; on the Worker, set routes to the Master’s node ID. IDs come from public identity JSON, not directory names or invented display names.

[relay]
control_node_id = "control"
endpoint = "https://control.example.test:7449"
routes = ["<worker-node-id>"]

routes requires 1–32 distinct IDs, excluding Control and the local node. Control and route IDs allow 1–128 ASCII letters, digits, -, _, : and .. The Relay endpoint must be an HTTPS origin without credentials, a path, query or fragment. Relay settings come from TOML; there are no dedicated Relay environment variables or CLI flags.

Nodes in routes always use Relay; other nodes use direct connections. Once Relay is selected, disconnection or authentication failure returns an error without falling back to a direct route. Task commands still require the Worker’s HTTPS --node-endpoint for the same inner mTLS connection; do not replace it with Control’s address.

Control reads control.toml from its data directory by default; --config selects another file. For example:

node_id = "control"
listen = "0.0.0.0:7449"
lease_seconds = 60
queue_capacity = 32
log_directory = "logs"
log_retention = 14
log_filter = "info"

Precedence is defaults, TOML, .env beside the configuration file, process environment, then --listen. Environment aliases are LYONBROWN_CONTROL_NODE_ID, LYONBROWN_CONTROL_LISTEN, LYONBROWN_CONTROL_LEASE_SECONDS, LYONBROWN_CONTROL_QUEUE_CAPACITY, LYONBROWN_CONTROL_LOG_DIRECTORY, LYONBROWN_CONTROL_LOG_RETENTION and LYONBROWN_CONTROL_LOG_FILTER. The default listener is 127.0.0.1:7449. Directory leases allow 1–3600 seconds, queue capacity 1–1024 and retained log files 1–365. Relative log directories resolve against Control’s data directory.

Alternatively, manage links with allowed_links = [] or [[allowed_links]] entries containing source and target in control.toml. When this field is present, serve atomically replaces the entire persisted allow graph at startup. Omitting it preserves links written by allow / deny.

cargo run -p agent-control -- --data-dir /path/to/control serve
cargo run -p agentd -- --data-dir /path/to/master
cargo run -p agentd -- --data-dir /path/to/worker

Run these in separate terminals or on their respective nodes. Control authenticates outbound streams with mTLS and checks directional permissions. Noise IK authenticates the end-to-end tunnel using paired public keys; ordinary mTLS and TaskService run inside that tunnel. Control sees source/target IDs, link identifiers and ciphertext sizes. It receives no task plaintext and executes no models or tools. Queues are bounded and are not durable task queues; successful enqueueing does not confirm Worker execution.

ControlService exposes leased Register / Resolve operations, but the daemon’s Relay runtime only opens an outbound stream. It does not automatically register, renew leases or resolve directory entries. These explicit routes do not depend on directory registration; directory records cannot establish pairing trust.

Dispatch, approvals and recovery

Manage tasks through the CLI connected to the Master. First create a Master session and start a run; dispatch requires --parent-run to identify a run in that session with status running. Preserve preselected UUIDs for the Task and Attempt, plus a stable idempotency key.

cargo run -p agent-cli -- --data-dir /path/to/master task dispatch \
  --node-id '<worker-node-id>' --node-endpoint https://worker.example.test:7448 \
  --session '<session-id>' --parent-run '<active-run-id>' \
  --task-id '<task-uuid>' --attempt-id '<attempt-uuid>' \
  --idempotency-key '<stable-key>' --instructions 'Inspect the assigned workspace' \
  --capability workspace.read --deadline-seconds 3600

The deadline allows 1–86400 seconds. The Worker uses its own model, credentials and Harness, creating an isolated workspace and session under worker-workspaces/<task_id>/<attempt_id>. It does not copy the Master’s session history or workspace files. Task capabilities can only reduce the Worker’s available tools. Writes still require local approval on the Worker through a client connected to that Worker; Relay and Master result acceptance cannot bypass tool approval.

A successful Worker attempt leaves the Task awaiting_acceptance. Explicit Master acceptance makes it completed:

cargo run -p agent-cli -- --data-dir /path/to/master task get '<task-uuid>'
cargo run -p agent-cli -- --data-dir /path/to/master task reconcile '<task-uuid>' \
  --node-id '<worker-node-id>' --node-endpoint https://worker.example.test:7448
cargo run -p agent-cli -- --data-dir /path/to/master task accept '<task-uuid>' \
  --node-id '<worker-node-id>' --node-endpoint https://worker.example.test:7448 --accepted true

task list --session <session-id> pages through Master’s records. task cancel takes the same target arguments as reconcile. Reject results with task accept … --accepted false.

After disconnects, timeouts or lost cancellation responses, retain the original Task, Attempt, key and target. Use get for local state and reconcile to check that same remote attempt. The Master persists unknown attempt outcomes as uncertain. Relay reconnection restores transport without automatically reconciling business state or replaying requests. Do not dispatch fresh identities to bypass an unknown outcome. On restart, the Worker also marks unfinished attempts uncertain without re-executing them. See Sessions, tasks and recovery.

Revoke access and investigate failures

  • Deny one direction with agent-control --data-dir /path/to/control deny <source> <target>. Deny both directions for bidirectional isolation. If allowed_links is configured, update it too so restart does not restore the old graph.
  • Revoke a node on Control with agent-control --data-dir /path/to/control revoke <node-id>. Active streams recheck trust; restart the listener to remove its old CA root.
  • Revoke a daemon’s paired identity by stopping that daemon, running agentd --data-dir /path/to/node peer-revoke --node-id <node-id>, then restarting its listener. Identity rotation requires another export, independent verification and pairing on the relevant receivers.
  • For mTLS failures, check public identities, complete pairing fingerprints, trust on both ends and listener restarts. Keep identity verification enabled.
  • For Relay failures, check both outbound streams, both route sets, Control’s bidirectional links and paired identities. target has no active outbound relay stream means no active target stream; backpressure errors mean a bounded queue could not accept data in time.
  • Inspect structured logs in each data directory for control.listen, control.relay, relay.transport and task IDs. Do not include tokens, private keys or full task plaintext in diagnostic material.

Native desktop execution boundary

CLI and Desktop forward their default-disabled native-computer feature to agent-computer-runtime/native. Native SDKs require the explicit native feature. agent-computer-runtime/native enables agent-computer/native and the attach_native factory. Default builds retain the protocol, engine and injectable attach_host without capture or input SDKs. The daemon uses this default dependency path.

Native target discovery reads metadata without capturing pixels or requesting OS permission. It checks the interactive session and existing screen permission before and after enumeration. Minimized and zero-sized targets are omitted; catalogs exceeding 512 entries are rejected. Labels have control characters removed and are limited to 512 characters. DesktopTarget Debug output omits labels that may contain private content. Window descriptors retain the process ID; attachment checks window and process IDs to reject replacement windows. Titles and geometry are checked against fresh observations, rather than treating the old catalog as the current screen.

agent-computer encapsulates screen observation, input and desktop leases. agent-computer-runtime retains prepared actions in process and checks their daemon Session, Run and owner_epoch binding. Execution messages refer to the original preparation, action identity and content digest; they cannot replace the input. After approval, the runtime observes again using the original lease and limits. Changed content, an invalid lease or cancellation prevents input. The preparation is consumed before refresh or input, so a failure cannot replay that action.

The client-side library can embed a native host through attach_native. Before attachment it checks the authenticated daemon node and selected session ownership. The handshake fixes the desktop scope; the daemon verifies identity again and records the session’s owner_epoch. A session permits one host attachment. Model tools pin the attachment generation. Every operation checks Run state and session ownership before dispatch and after response; a reconnect cannot replace the host already selected by a run. Attaching grants no capture or input permission.

An attachment permits one pending command. Requests for the same attachment generation queue serially, so renewal cannot preempt a dispatched command. The wait supports cancellation and a 35-second deadline; dispatch checks the attachment generation again. The daemon checks replies against the request, host, attachment generation, Session, owner_epoch, private protocol version and expected reply type, then validates lease, scope, image, window and AX node bounds. Invalid replies or disconnects cancel the attachment without replaying input. Native calls and message codecs run on a blocking worker. Calls already inside the OS still need to drain; cancellation does not terminate their threads. A native host holds a file lock in the user data directory keyed by the OS graphical session. Changing daemon node identity or a configurable client data path cannot split this lock. The executing worker retains it until the call drains.

Native runtimes in the same process share a desktop lease registry. Token-specific revocation validates and cancels the exact live token under one lock; an expired controller cannot revoke its replacement’s lease. Private postcard protocol version 2 includes exact-token RenewLease. Renewal extends only the current unrevoked, unexpired token; it cannot acquire another token or restore expired control. The packet limit is 68 MiB, accommodating up to 64 MiB of RGBA pixels plus metadata. Oversized frame prefixes are rejected before payload allocation. The daemon limits capability replies to 4 KiB, observation replies to 68 MiB, and other replies and requests to 16 KiB. The daemon still owns durable approvals, execution intents and replay protection across process restarts; in-process records cannot replace persistent records.

The daemon provides Harness computer_observe and computer_act through this authenticated connection. See computer tools for availability checks, exact approval and durable receipts. CLI/TUI and Desktop expose explicit target selection and session attachment; see native computer attachment. The configuration switch alone does not create a native host. These components do not establish client-to-Harness native-control acceptance. See the macOS session checks and limits below. Windows and Linux adapters also require their platform permissions; actual runtime acceptance on those platforms remains incomplete.

macOS reads the calling process’s CoreGraphics session and requires it to be on the console with login complete and a CGSSessionUniqueSessionUUID that parses as a non-nil UUID. Using maintained objc2 bindings, it also reads the IORegistry root and requires an explicit IOConsoleLocked = false. Either IOConsoleLocked or CGSSessionScreenIsLocked being true returns Locked. A missing or malformed IOConsoleLocked, or a missing or invalid session UUID, returns SessionStateUnknown. Each session check reads and validates snapshots before and after the lock probe; a changed snapshot is rejected. The lock fields are macOS implementation fields. This is the project’s chosen compatibility policy, not an Apple-documented lock-state guarantee.

Once the native backend observes a lock, unreadable session state or changed session identity, it stays revoked. Unlocking cannot restore control through that backend; a fresh explicit attachment is required. Session checks, screen capture and input remain separate OS calls; before/after validation does not guarantee atomic capture and input. See crates/agent-computer/src/native/macos.rs, session.rs and mod.rs.

Run locally during development

The repository’s .cargo/config.toml defines the dev alias. It uses Cargo directly, with no additional task runner to install. Run one command from the repository root to build the required binaries, start a development agentd and open the client:

cargo dev desktop
# Or open the terminal UI:
cargo dev tui

Run cargo dev tui in multiple terminals alongside Desktop. Clients using the same data directory, address and configuration share one development agentd. The command supplies the connection address and credentials automatically; no separate daemon startup is required.

Defaults are .local/dev/agentd for persistent development data and http://127.0.0.1:7547 for the endpoint. cargo clean preserves the data. These commands supervise foreground development processes without registering or replacing OS services. The terminal that first starts the daemon keeps its supervisor running after its client closes. Press Ctrl+C there to stop the development daemon. Later terminals reuse the daemon and can exit their clients without stopping it.

Startup checks are serialized for each data directory to prevent concurrent clients from creating multiple daemons. Reuse requires an authenticated handshake and matching node identity, protocol, build and configuration. To use a new build or configuration, stop the development daemon in its original terminal and run the command again.

cargo dev desktop --data-dir .local/dev/demo --listen 127.0.0.1:7548 --config /absolute/path/dev.toml
